# Working on baton

baton runs a multi-phase Claude Code plan unattended by hosting `claude` in a pseudo-terminal it owns. The design is [`docs/design.md`](docs/design.md). The evidence is in `docs/research/`, one file per question, each with a summary at its top. Read the one that applies before changing compaction, escalation, hooks, jobs, phase agents, usage limits or the host loop: several obvious-looking alternatives were tested and **do not work** (changing `autoCompactWindow` mid-session, scheduling `/compact` with CronCreate, hiding baton's agent type from the session).

## Non-negotiables

- **The live terminal stays visible.** baton is a byte-for-byte passthrough; nothing may draw over or replace the Claude Code TUI.
- **No runtime dependencies for users.** One static Go binary (`CGO_ENABLED=0`), sh/PowerShell launchers, and the plugin's mod, which Claude Code runs. No tmux, no AppleScript, no Node/Python.
- **Control flow lives in host code, not in model judgment.** If a step only happens because a model remembered to do it, it is a bug waiting to happen; make a hook or the host do it. No model spawns, wakes, steers or answers for a phase agent.
- **Nothing waits on the human for what baton can decide** (v0.8.3, v0.8.4, v0.8.6). With no deadline, baton waits on them only where they chose it (Pause baton, `/baton pause`, a `max_auto_decisions` they set, a phase agent they stopped twice whose work is not done, while the rest of the run can move: once nothing else can, baton takes the phase back for the lead `escalation_timeout` later) or where nothing in baton can answer (a permission prompt, the usage limit until its reset, a login or billing error, a refusal). A run that was working on its own goes on 2 minutes after the usage limit's reset (the resume timer, v0.8.15), and the weekly wind-down ends at the weekly reset; the human cancels either by their own act, a pause or a prompt (which pauses the run), and `/baton run` arms it again. Every other wait has a deadline whose answer is the model's side, and none is longer than 20 minutes but a block's: a question of baton's at `escalation_timeout` (10 minutes, at most 20; a proposal's own `--wait`, 5 to 20), the lead model's own question where the mod runs, a Wait for me hold after `Timing.HoldLapse` (20 minutes with no word from the human), and a block after `Timing.BlockLook` (30 minutes), when the model looks again for a safe way on and proposes it. A phase agent's block question says what the rest of the run does meanwhile (v0.8.16, `decide.RunWait`, `loop/runwait.go`): that it goes on, or, when nothing else can move (`state.Moves`), that the whole run waits, naming the phases behind it (`run_waits` on `relay_asked` and `relay_issued`); in a real run a block's questions told a sleeping human for nearly five hours that the rest went on, while nothing could. An outward proposal (`decide.Outward`) is answered Not now at its deadline (`decide.NotNowRule`): the model does it only if it is safely reversible and stays in the project. A question that never reached the screen is answered by the host's loop (`Loop.lapse`, `hooks.Lapse`). Nothing gives up: retries go on (a crash loop backs off to every 15 minutes), and a stalled session still gets its results and its reminders. A new hold, cap or question needs a deadline that picks the model's side, or an opt-in setting: a risk hold lifts at `escalation_timeout`, a look-in held for the advisor goes at `Timing.AdvisorWait` (60 seconds), and every refusal-once of v0.8.7 (a gate out of proportion, a background check, what a phase left running) lets the same call through the second time; a long repeat let through without a reason (`--why`) is told to the human (`gate_unexplained`, v0.8.11).
- **Hooks fail open.** For Claude Code hooks, exit code 2 means *block*, and so does a Go panic or a `flag` parse error. Every `baton hook` path recovers panics, uses `flag.ContinueOnError` and exits 0 on internal errors; only the deliberate rewake path exits 2. Each hook event has a test proving a panic exits 0, and every hook of the mod has a `.catch` that lets the event through.
- **Dormant unless hosted.** Hooks, the CLI and the mod do nothing unless a live baton host is above the session, apart from `/baton start` handing a plain session over (package `elevate`). `BATON_HOST=1` alone is not enough (v0.8.4): Claude Code's background service passes it on to sessions no host drives. Package `hostcheck` also wants the host's pid, recorded at `.baton/hosts/<instance>.pid`, among the asking process's ancestors, and trusts the variable alone only where processes can't be read. A session that only inherited the variables is told once how to come back (`inherited_notice`), and its `WorktreeCreate` still gets a plain worktree, since baton's hook replaces Claude Code's own; the mod stays dormant, as no host answers its hello.
- **Compaction moves only on proof.** A phase agent's `PreCompact`, `SessionStart(compact)` and `PostCompact` carry no `agent_id` and look like the lead's, so those hooks only log `compact_seen`. A `state.Proof` comes from the mod's report (the lead's compaction) or a new `compact_boundary` in a loop's own transcript.
- **No git operation baton runs, or asks a model to run, rewrites or discards work.** Landing merges the run's branch into a phase's branch and never rebases it: a rebase can drop a resolved conflict without a word. baton runs every merge itself, and a model only resolves files, adds them and commits (v0.8.16): auto mode refused a rebase (v0.6) and a merge (v0.8.14, 4h50m with the whole run waiting) that baton had asked an agent to run ([`visible-workers.md`](docs/research/visible-workers.md)). baton's merge starts only on a worktree with no uncommitted change to a tracked file. One that stops on conflicts in a phase agent's worktree (a landing's, `baton sync`'s) is left in progress there for that agent (`gitx.MergeError.Kept`), told never to run `git merge`, `rebase`, `reset` or `merge --abort`; one that stops for any other reason (a merge commit that cannot be signed) is aborted. Nothing is lost either way: a merge started on such a worktree holds nothing but the merge, so `git merge --abort` gives back the branch, index and files exactly; baton never runs it once a model may have resolved files; and the merge commit keeps both parents, so no commit is rewritten. The one commit baton makes into a project is a plan's record file (v0.8.7): a new commit of that one path (`git commit --only`), never over a dirty file.
- **baton types nothing where the mod runs, and never Ctrl-C while an agent may be live.** The mod compacts the lead and submits baton's lines (`bridge.Compact`, `bridge.Submit`) with the human's draft left in the box, and nothing types into a dialog ([spike 35](spikes/35-mod-drives/)). In serial mode v0.7's typing stays (`/compact`, baton's lines), but no digit goes into a dialog: on Claude Code 2.1.30x a Bash prompt's `3` is "Yes, and switch to auto mode" ([spike 39](spikes/39-escape-answers/)), so the host answers its own question by Esc, only while that question is the only dialog open, and records its default itself (`loop/watch.go` `answerOwnQuestion`, `hooks.Lapse`; `auto_answered` with `key: esc`), since no hook reports a dismissal. A draft is cleared only while no agent may be live: one Ctrl-C at the prompt stops every background agent for good, baton's and the model's own.

## Layout

- `cmd/baton/` is the entry point; `internal/<pkg>/` has one package per concern. `decide` owns the escalation policy and every model-facing and human-facing sentence (the band and the board too). `loop.Loop` drives the lead, and `loop.Coordinator` owns the run: phase agents (`fleet.go`, a `loop.Agent` each), the merge queue (`merge.go`), agents' questions (`relay.go`), holds on new agents (`room.go`), retiring (`retire.go`). `state.Project` maps each session to its run (`.baton/runs/<id>/`). `transcript` reads Claude Code's transcripts, read-only and best effort. `risk` scores phases for the risk ledger, and `leftover` finds what a phase left running. `machine` and `procs` read the machine and processes without cgo, `ps` or `lsof`, and callers take the reading injected, so no test depends on the machine. `hostcheck` says whether a live host is above the asking process, reading its ancestors one at a time (`procs.Parent`), never the process table; each command keeps its answer (`cli` `IO.Hosted`), and no cache is kept on disk. A session with no plan of its own carries on a run of the same plan file that no live host owns (`cli/carry.go`, `state.Project.Orphans`, `run_carried`).
- **Phase agents** (v0.8, [`visible-workers.md`](docs/research/visible-workers.md)): each phase beside the lead is a `baton:phase` agent of the lead's session, with a sub-run `.baton/runs/<run>/workers/<phase>/` (`Store.Root` its worktree). No code holds two store locks at once. `Dispatch` finds the loop first: an `agent_id` linked to a phase agent is its sub-run, Claude Code's own forks of one change nothing, anything else is the lead's. Learned on real Claude Code 2.1.296:
  - every delivery to an agent is a message, held for its next tool round; a resumed agent gets nothing of `SubagentStart`, so baton's deliveries come at its next tool call or its stop;
  - the type stays offered (Claude Code resumes no agent of a type the session doesn't offer), and `PreToolUse` refuses a model's own call to it;
  - the worktree-isolation guard refuses a quoted command starting with a shell or git, so a phase agent gives a gate as words after `--`, and `PreToolUse` rewrites a quoted one into that form (`gate_as_words`);
  - a hook's `prompt_id` is the session's latest prompt, so a phase's worktree is told from a model's by the open Agent calls (`Runtime.AgentCalls`);
  - `/clear` ends every agent, and baton starts each unfinished phase again (on 2.1.300 it kills an agent's running command, and the agent ends after finishing its turn under the new session id, which `fleet.go`'s `cleared` waits for);
  - in auto mode an agent's end also comes back to the lead as a peer prompt (`<agent-message from="P3">`, then `[Subagent hand-back]`), which the mod drops; `TurnSource` counts that text as a system prompt, never the human's.
  - since 2.1.302, in auto mode, an agent hands its report back with a tool (`SubagentHandback`) that "ends your run" and ends its turn whatever `SubagentStop` says, and one that ends a turn without it is sent back to call it (up to three times); a message still resumes it. So `PreToolUse` decides a phase agent's hand-back as its stop would be decided (`hooks/handback.go`, `handback_refused`): refused with the stop's words while its phase is not reported and nothing it waits on will wake it (counted with the stop's refusals, `MaxStopBlocks`), or to give it a result or a message due first; let through otherwise. `decide.PhaseAgentPrompt` says a hand-back ends only its turn.

  Learned from a real run (v0.8.2): nothing compacts a phase agent, so a sub-run never owes a boundary. A red verification (its gate after `baton done`, or a landing's re-verification) takes the phase up again in place (`state.Retake`, from `settle`, the agent's tick and its stop), and the result goes to the agent. A new agent starts `Fleet.Ramp` (2 minutes) after the newest live one, since the machine's readings lag the load an agent brings. Since v0.8.15 a worker waiting to land takes no agent slot (`planWorkers`; one handed back counts again), and at the cap a ready phase is held as `state.HoldCap` (`state.Hold.Cap`), which the board and `baton watch` show ("ready: all 6 agent slots at work", `decide.SlotsAtWork`) and nothing announces; the weekly wind-down's `state.HoldWeekly` is checked before it. A landing's conflict reaches its agent with, under each path, the commits that changed it since the merge base and the phase that landed each (`decide.LandConflict`, `Coordinator.conflictHistory`, `gitx.LogPaths` before the lock). Since v0.8.16 a phase agent runs no git operation on its branch (`decide.WorkerIntro`): baton merges for it. A landing's conflict is left as a merge in progress in its worktree (`mergeIn`, `land_returned` with `kept`), and the agent resolves, adds and commits it. A phase agent's `baton done` over a merge in progress commits it once nothing is unmerged and no conflict marker is staged (`cli/mergedone.go` `concludeMerge`, `gitx.CommitMerge`, `merge_concluded`, told to the lead), and is refused otherwise, naming the paths, whatever `--keep-dirty` says (`decide.MergeUnfinished`); a phase that reaches its landing with the merge still in progress goes back to its agent as no new conflict (`loop/unfinished.go`, `decide.LandUnfinished`, `land_returned` why `its merge is not finished`). `baton sync` (`cli/sync.go`, phase agents only) merges the run's branch into the agent's on its say-so, refused over uncommitted tracked changes (`gitx.Uncommitted`) or a `--here` gate running there, and a conflict is kept as at a landing (`decide.SyncConflict`; `synced`, told to the lead). A fresh agent whose worktree holds a merge in progress is told of it first in its brief (`hooks/mergeleft.go`, `brief.Input.Merge`, `decide.MergeInProgressBrief`), since the message about it may have gone to the agent it replaced. The lead's standing words forbid making the human a courier between sessions (`decide.NoCourier`, the lead's `Words.Reporting` and `Closing` alone). A `verify --here` gate in an agent's worktree holds one of the project's lane slots while it runs (`lane.Job.Here`, with `BATON_LANE` set), so here and lane gates together never exceed the slots; with no `.baton-lane` there is one. A plan change reaches each live agent as a message, once per change to the standing rules or its section (`loop/replan.go`). Since v0.8.6 a phase agent's loop skips the screen gate, since it types nothing (`Loop.agentLine`), and the room log changes only when the kind of room the machine lacks (busy, swapping, memory) changes and has held for `Fleet.RoomSettle` (30 seconds).
- **Phase handles** (v0.8.6, [spike 40](spikes/40-agent-handles/), Claude Code 2.1.301): the mod names each phase agent for its phase (`bridge.Spawn`'s `Name`), and that name is the human's handle on it.
  - **Phase ids are agent names** (`plan/names.go`): 1–32 letters, digits, `_` or `-`, starting with a letter or digit (no dot, `P8b` not `P8.5`); none Claude Code keeps (`main`, `team-lead`, `user`, `system`, in any case), none of an agent id's shape; no two equal ignoring case, since SendMessage falls back to a match ignoring case. `plan.Build` refuses any other with why (the lead's `ExitPlanMode` turns the plan back once, `plan_unbuilt`; an approval or `baton attach` of it attaches nothing, saying why), and so do a replan's draft and a phase the plan file adds; ids the running plan already had pass as they are (`Rebuild`, `Follow`), and a carried run keeps its own. `Plan.Named` is the phase a name addresses, ignoring case.
  - A name points to the latest agent given it (the typeahead, SendMessage by name), so `PreToolUse` refuses a model's own Agent call, the lead's or any agent's, named for one of the run's phases ignoring case while a plan is attached (`decide.AgentNameIsPhase`, `agent_name_refused`, after the `baton:phase` type's refusal); the mod's own spawn (`modCall`) never comes there. baton sends to an agent by its id.
  - **`@<phase> <words>` at the lead's prompt** writes to that phase's agent. Claude Code sends `@name` at the main prompt only to agent-team teammates, so the lead's `UserPromptSubmit` routes it (`hooks/handles.go` `addressed`), by shape alone (the hook's input names no origin): a prompt `TurnSource` takes for the human's, a leading `@<id>` and whitespace, the id one of the run's phases. `state.Addressee` says where the phase stands. For an agent at work (`WorkerWorking`, its `AgentID` in the bridge's `agents.json`, not retiring) the words are queued (`State.ToAgents`, `state.HumanWords`; the same words still queued, once) and the prompt is blocked (`decision: block`, reason `decide.SentToAgent`): no turn, nothing in any request, and the reason, under Claude Code's own frame, is all the human sees (a `systemMessage` beside a block shows nowhere, and `continue: false` lets the words into the conversation: never use either). The coordinator sends them first in each step (`loop/words.go` `toAgents`) through `bridge.Send`, framed as the human's (`decide.HumanToAgent`); the mod's ack takes them off, one unacked is sent again after `sendWait`, and words no agent took (it ended or was stopped first, or Claude Code refused the message) go to the lead as `MessageWords` mail, announced. Claude Code keeps a blocked prompt in the box, where a second Enter sends it again, so `emptyAfter` (1 second) later the mod empties it (`bridge.Empty`), only while it holds exactly that prompt. Every other stand (not started, done, landed, the lead's own, stopped, starting, replaced, landing, retiring) wakes nothing: the prompt goes on to the lead's model with `decide.WordsForLead` as context, and the human gets `decide.WordsToLead`. Each step logs `human_to_agent` (`routed` agent or lead; `step` queued, sent, acked or unsent; `stands` and `why` for the lead).
  - **The retired-agent guard:** the human's typing in an agent's own view wakes it whatever it is, with no hook of the lead's, and an agent whose unchanged worktree Claude Code removed is resumed in the lead's checkout. So every agent baton lets go of for good (`RetireWorker`'s forget, `respawn`, `afresh`) is recorded (`state.Project.LetGo`, a `retired/<agent>` link swept with its run), and the `Handlers` wrapper refuses its every `PreToolUse` (`decide.LetGoRefused`) and lets its other hooks, its stop too, through with nothing recorded; `retired_agent_woke` is logged once per agent, in the lead's run.
- **QA phases** (v0.8.3): a phase with `Type: qa` under its heading (`plan.Phase.Type`, read beside `After:` by `parseHead`) runs the full checks; with `aggregate_qa` on (the default, `BATON_AGGREGATE_QA`), the phases before one are briefed to run focused checks (`brief.qaGuide`, `decide.QAFocus`), and `baton verify` and `baton await` ask once about each job queued before it (`decide.QAAsk`; `--qa` flags an early full check, `qa_early`). A red result there says other phases' work in progress may be why (`plan.QAAhead`), with `baton done --despite-red` for what is not the phase's to fix. A phase agent's narrowed plan keeps the name of its QA phase (`Plan.QAFor`). Since v0.8.15 a QA phase goes to a phase agent where the run has them (`State.HasAgents`: `Runtime.Fleet`, which the coordinator records for a host with a fleet, no serial mode, and a run branch): `state.Next` passes over a ready one and `NextWorker` gives it to an agent, even as the last phase; it is the lead's again once an agent of this generation failed on it, or when parked, and `Fleet.next` lets it through a risk hold. A QA phase's narrowed plan (`Plan.Only`) keeps `Plan.QASince`, so its agent's brief names what it checks. Once every other phase is done and the QA phase's session hears `@` words, the coordinator tells the human once a generation that a review now reaches it in time (`state.ReviewReady`, `decide.ReviewReadyLine`; `review_ready` announced, pushed and logged; `Runtime.Review`).
- **Plans at approval** (v0.8.5): a plan with one phase heading attaches (`plan.Shaped`); one with none is ordinary plan-mode work and is left alone. `plan.Suggest` makes every anchor occur once in the document (the heading line, else with its line end, else extended by the lines under it) and passes over fenced code, so a plan that quotes its own headings attaches; `plan.Added` reads an anchor's first line. At a hosted lead's `ExitPlanMode`, each once per plan: a plan with phase headings that would not build (`plan.Build`: an id that cannot name an agent, or one equal to another ignoring case, an `After:` naming an unknown or later phase, an anchor that still occurs twice) is turned back with why (`hooks/planbuild.go`, `Runtime.UnbuiltAsked`, `plan_unbuilt`), and the same text again goes on; then the plan's first `ExitPlanMode` is turned back to flag competing instructions (`directives_asked`) and, for every plan since v0.8.7, to check its gates against `decide.GateRules`, listing its QA phases with the phases each covers and asking that each sit at a real seam (`decide.GateCheck`, `hooks/gaterules.go`; `directives_asked` gains `gates`, `qa_phases` and `extra_qa`; every brief carries `decide.GateHabits`), and, for a plan that is mostly one chain (`plan.Shape.MostlyChain`: at least `plan.ShapeMinPhases`, 6, phases and a longest chain over `plan.ShapeChainShare`, 0.6, of them), to check each link of that chain against the shape rules (`decide.ShapeCheck`; `directives_asked` gains `phases`, `longest_chain`, `width` and `shape_flagged`). The model may resubmit unchanged, saying in the plan why the chain is real. Every later `ExitPlanMode` of it shows the human its shape in one line (`decide.PlanShape`, `plan_shape`; none for one phase). The shape rules are `decide.ShapeRules` and the skill's `plan` section: keep the two in step, and bump `plan.RulesVersion` when they change (below). Keep `decide.GateRules` in step with the skill's QA bullet and gate line too; v0.8.7 added them without a bump (`RulesVersion` stays 1), since the structural replan a bump brings can only reorder phases and would not apply them.
- **The plan moved out of Claude Code's way** (v0.8.6, [spike 38](spikes/38-plan-file-reference/)): after every compaction Claude Code attaches the session's plan-mode file, `<plansDirectory>/<slug>.md`, in full (`plan_file_reference`) for as long as it exists, on top of baton's brief, which quotes what the phase needs of it; in a real run that was about 32k tokens of every phase's starting context, and no setting turns it off. So when a plan baton attaches is that file (`state.Aside`: the slug from the session's transcript, `transcript.Slug`, read before the lock by `Project.LookAside`) and no other live run's plan, baton renames it in its folder to a name from the plan's title (`plan.MoveAside`, `plan.AsideName`: unique, never over a file), follows it there, keeps the old path as `plan_origin` in `plan.json`, and says so (`decide.PlanMoved`; `plan_moved` with `from`, `to` and `by`, or `plan_not_moved` with why). It moves at the hooks' attach, at `baton attach`, and, for a run attached before v0.8.6, before the lead's next compaction that starts a phase, once (`loop.moveAside`, `State.PlanLooked`). An approval of the origin is a revision of the run's plan, since Claude Code writes the session's next plan there, and is moved aside in its turn (`PlanQuestion.Origin`). Carrying a run matches its plan file or its origin.
- **Replans** (v0.8.5, package `replan`): the lead's model restructures the phases not started, in the session; the host decides when, and whether its draft stands. One opens only on a cue, never on a timer or the model's own initiative: the human's `/baton replan ["<what to consider>"]` (`baton replan`, done in that turn), or baton's own at the lead's phase boundary, whose brief comes before the phase's in the same fresh context (`hooks/autoreplan.go`, `replan.Due` and `replan.Auto`): `upgrade` when `State.RulesVersion` is below `plan.RulesVersion` (a run carried across an upgrade) and the phases not started hold a chain, once per rules version; `qa` when a QA phase is under way and the phases not started are mostly one chain, once per QA phase; `marked` once a phase marked `Replan: after` (`plan.Phase.Replan`, read by `parseHead` beside `After:` and `Type:`) is done, once per marked phase; `conflict` (v0.8.15, `state.ReplanConflict`) after `marked`, once per file that conflicted in a second landing while phases not started name it (`State.ConflictCue`, recorded by `state.CueConflict` as the `conflicting_file` look-in is left; `replan_opened` logs `files`), with `marked`'s limits. Each cue is settled once, whether a replan opens or not (`State.ReplanCued`, `replan_skipped`). The model edits `.baton/runs/<run>/replan/draft.md` and runs `baton replanned --notes …` (or `--none …`), which checks the draft against what its kind may change (`plan.Redraft`, `replan.LimitsOf`): started and done phases (`state.Frozen`) never change, and the unstarted phases' order and `After:` lines always may. `upgrade` and `qa` change only those (`replan.Structural`), and stand only if the unstarted part's longest chain got shorter or its width grew (`replan.Improved`; otherwise `replan_unchanged`, the plan file untouched); `marked` and `conflict` may also reword and split unstarted phases, never drop or merge them; the human's may also add and reword phases, and drop phases or change the goal sections only as far as their words ask, naming each dropped phase in its notes. A draft that passes is written over the plan file and followed (`plan_replanned`), and recorded as a decision whose undo copies `replan/<n>.md` back (`replan.Restore`, `replan_undone`). Every replan is compared with the approved text, `replan/0.md`, and `baton status` lists each against it. While one is open, or owed at the lead's boundary (`replan.Owed`, `Fleet.AutoReplan`), no new phase agent starts (those at work go on), and the Stop hook leaves the plan file alone; one open for `Timing.ReplanMax` (20 minutes) lapses (`replan_lapsed`) and the plan goes on as it was. `plan.RulesVersion` numbers the planning rules (1 since v0.8.5): a release that changes the shape rules or the skill's planning guidance bumps it, so each run carried across that upgrade gets one structural replan by the new rules. `auto_replan` (on by default; `BATON_AUTO_REPLAN`) turns baton's own replans off; `/baton replan` works either way. Since v0.8.6 the brief also lists, as information only, the pairs of phases not started that could run at once (no `After:` path between them) and name the same file, since they collide when they land (`plan.Paths`, `plan.Plan.Overlaps`, `decide.ReplanBrief.Shared`; `replan_opened` logs `shared`); what a replan may change is the same. The question about a plan approved mid-run is `state.PlanQuestion` (`plan_question_asked`, `_held`, `_resolved`, `_waits`): "replan" names this feature alone. Its options are Wait for me, Start the new plan from P0, then the default third (Continue with the revised plan, or Keep the current run; `decide.PlanQuestionDefault`), so a stray Enter holds the run and lapses into the default, and no single key sets a run's progress aside (v0.8.6).
- **Context valves** (v0.8.6, `internal/valve`, `hooks` `contextValves`, [`context-window.md`](docs/research/context-window.md)): three lines, each a percentage of the limit (the model's window, or the `--autocompact` cap if smaller). At `notice_pct` (60, `BATON_NOTICE_PCT`) the model is told where its context stands and asked nothing (`context_notice`: additional context beside the tool result and a `systemMessage`, never a block; `decide.ContextNotice`); at `checkpoint_pct` (80) it is asked to checkpoint at its next safe point (`context_nudge`), and again at every further tenth; at `warn_pct` (90, never under `valve.WarnFloor`, 200k) the lead's model puts the human the context question (`context_warning`), answered Keep going at `escalation_timeout`. Each fires once a stretch, a later one standing for those before it, and re-arms when the context falls a tenth of the limit below its line; a phase agent gets the notice and the nudge. When any line would come at or after Claude Code's own compaction (`Limits.AutoAt`, `valve.AutoCompactMargin`, 33k, below the limit), every line is its percentage of `AutoAt` instead. With 810k: 486k, 648k and 729k, and Claude Code at 777k. The checkpoint moved from 60 to 80 because a compaction restarts a lead at about 180k: 60% left about 300k of room a stretch, and a real run's lead checkpointed 9 times mid-phase against 7 boundaries. A `checkpoint_pct` set in a config keeps its value.
- **The stall alarm** (v0.8.2, `loop/stall.go`): each loop's watchdog stays quiet while it waits on something that ends by itself, so the coordinator also looks at the run as a whole, about once a minute, with `workers: 0` too. With the plan running, nothing busy and nothing moved for `Timing.StallAfter` (20 minutes), it pushes one notice (`run_stalled`) naming what each phase left waits on. It is not an escalation, which would hold the lead's deliveries, and movement arms it again. Since v0.8.6 a running gate is busy while its log moves (`logMark`: size and modification time) or, with its log still, while its process tree used CPU since the alarm's last look (`Runners.Usage`, read only while the log stands still; no reading leaves the log to decide), as the hung check reads it: only a gate quiet in both is named hung. An `await`, and a gate waiting for a lane, are busy while their runner beats. Since v0.8.15 the weekly wind-down's wait is one it expects (`windWait`) only while nothing is under way (`state.UnderWay`), and its quiet counts from the wind-down's end (`Usage.WoundUp`).

Where the mod runs, a phase agent's permission prompt holds only that agent (`Loop.dialogHolds`, `state.Dialog.Phase`; spike 36), while serial mode holds on every dialog, since a typed key would answer the agent's prompt.
- **The mod** (`plugin/hooks/baton.js`) is a thin executor: it spawns and messages phase agents, asks the human, compacts the lead and submits baton's lines to it, empties the lead's input box of a prompt baton sent on to a phase agent, drops agents' reports before the lead's model sees them, draws the band, makes the host's model calls (`$.model.complete` from its poll, unawaited, for a `complete` command; [spike 41](spikes/41-model-complete/)), and reports what it sees; it decides and words nothing. It asks from its band's render hook, never its timer, and its `tool.call` hook settles baton's questions, and the lead model's own (`hooks.Bound`: its Recommended option, else its first), at their deadline ([spike 34](spikes/34-ask-deadline/)); serial mode leaves the model's own questions to the human. The host asks for the lead's compaction once its Stop hook has run, a moment before Claude Code counts the turn over, so the mod holds a compaction Claude Code declines while the lead's turn runs (by the mod's own `turn.start` and `turn.complete`) and calls it from that turn's `turn.complete`, once ([spike 37](spikes/37-compact-at-turn-end/)); past `HOLD_MS` (30 seconds, within the host's `modAckWait`) it acks the refusal, and the host asks again after the turn (`loop.redo`). Run `make mod-test` and `claude plugin validate plugin` before committing a change to it, and never edit it while a session that loaded it runs.
- **The bridge** (`internal/bridge`): numbered command files under `.baton/runs/<run>/mod/`, each for one host instance, and reports through `baton mod report`, each recorded once. A report of the lead's compaction (the ack of a compact command, compacting, compacted) is counted in the run's state before the bridge records it (v0.8.6, `cli/modcmd.go` `compactionFirst`, `state.CountOnce` with `Runtime.ModCounted`), so a report process killed between the two leaves the report with the mod, which sends it again, and it counts once; the bridge's record is read there without its lock (`Bridge.Peek`), so a report waits on two locks at most, and the mod gives a report and `baton board` 15 seconds (`REPORT_TIMEOUT_MS`, `VIEW_TIMEOUT_MS`), above two lock waits. No hello from the mod, or one in another `bridge.Protocol`, means a serial run (`loop/mod.go`); after a restart of a run whose mod said hello, the host waits up to `Timing.ModHello` for the new claude's mod before it gives the session anything. When the host drives another run (a carried run, `Loop.drive`), it issues `bridge.Moved` in the old run's bridge; the mod says hello on the new one and starts its command count afresh, since the count is per run. A `bridge.Complete` command (v0.8.7) is a model call for the advisor and the risk assessment: its ack, cut at `bridge.AnswerCut` (4,000), is kept for its issuer in `Record.Answers`, not the inbox, and `loop.Complete` (the lead's run store only) polls for it with no lock held, voiding the command at its deadline (`*loop.Unanswered{Why}`: `no-mod`, `serial`, `timeout`, `api-error`, …); calls in flight live in the mod's store and are acked interrupted on reload. An old mod acks "no such command", so `bridge.Protocol` stays 2.
- `plugin/` is the Claude Code plugin: the skill, the launchers, the Stop hook that finishes `/baton start`, and the mod. `SKILL.md` is a stub that loads `internal/skill/skill.md` from the binary, so edit that, and never put `$ARGUMENTS` in the stub's inline command ([spike 18](spikes/18-skill-inject/)). Keep it under 29,500 characters (`TestTextFitsClaudeCodesInlineOutput`): Claude Code gives an inline command's output past 30,000 to the model as a file with a 2KB preview. `.claude-plugin/marketplace.json` makes this repo its own marketplace.
- `spikes/` holds archived experiments. Don't import from them.

## Commands

```sh
make build      # ./dist/baton for this machine
make test       # unit tests
make mod-test   # baton's mod under Claude Code's test kit (needs claude; calls no model)
make cross      # all release targets into ./dist
make e2e        # real-claude scenarios (needs BATON_E2E=1, costs a few cents)
make release-prep VERSION=v0.1.0   # pin checksums + plugin version, then commit and tag
```

End-to-end tests run real `claude --model haiku` and assert on `events.jsonl` and hook logs, never the screen. Each session has its own `BATON_HOME` and `GNUPGHOME` and loads this repository's plugin with `--plugin-dir` (`noModPlugin` for serial mode). The harness sets `BATON_WORKERS=0` unless a scenario calls `StartAgents`, `BATON_TEST_LOAD=0`, `BATON_AGENT_RAMP=5s` (phase agents start 2 minutes apart otherwise), and `BATON_ADVISOR=0` and `BATON_RISK=0` (unit tests cover the advisor and the ledger); `BATON_ABANDON_AFTER` shortens the wait before a run counts as abandoned, and `BATON_HOLD_LAPSE`, `BATON_BLOCK_LOOK`, `BATON_RECOVER_AFTER`, `BATON_RECOVER_EVERY` and `BATON_REPLAN_MAX` the holds, blocks, crash backoff and replans. `BATON_AUTO_REPLAN=0` keeps baton's own replans out of a scenario that would cue one. `BATON_NOTICE_PCT` and `BATON_CHECKPOINT_PCT` move the context valves (`0` turns one off; with a small `--autocompact` cap every line moves before Claude Code's own compaction), and `BATON_WARN_TOKENS` sets the context question's line. Plan mode writes into `~/.claude/plans` unless the scratch project sets `plansDirectory`, so every scenario that plans calls `PlansHere`, which sets it to `plans/` inside the project and keeps that folder and the settings file out of git. `Session.ApprovePermissions` stands in for the human on the model's own permission prompts only, leaving every question of baton's to its deadline. Allow rules name the exact command, since auto mode drops a broad one like `Bash(sh:*)`. `BATON_E2E_SONNET=1` adds the Sonnet scenarios. Run one `go test` process at a time: the mod's store file in `~/.claude` is shared. The sessions take the permission mode from your own Claude Code settings, so in auto mode agents' ends come back as hand-backs the mod drops (`mod_dropped`). Claude Code's Bash tool ends a foreground command after 2 minutes unless the model sets a timeout, so a scenario's plan that waits longer asks for one (`BATON_FOREGROUND_MAX` takes at most 10m).

## Conventions

- Go: standard library first; a new dependency needs a reason (current: `creack/pty`, `golang.org/x/term`, `golang.org/x/sys`, `gofrs/flock`).
- Commits: [Conventional Commits](https://www.conventionalcommits.org/), one coherent unit per commit, so `git log` reads as the story of the project.
- Tests: table-driven, next to the code; time-dependent logic takes an injected clock; no test provokes a refusal.
- Every user-visible action baton takes is announced in the session (`systemMessage` or the band) and logged to `events.jsonl`.
