# Working on baton

baton runs a multi-phase Claude Code plan unattended by hosting `claude` in a pseudo-terminal it owns. The design is [`docs/design.md`](docs/design.md). The evidence is in `docs/research/`, one file per question, each with a summary at its top. Read the one that applies before changing compaction, escalation, hooks, jobs, phase agents or the host loop: several obvious-looking alternatives were tested and **do not work** (changing `autoCompactWindow` mid-session, scheduling `/compact` with CronCreate, hiding baton's agent type from the session).

## Non-negotiables

- **The live terminal stays visible.** baton is a byte-for-byte passthrough; nothing may draw over or replace the Claude Code TUI.
- **No runtime dependencies for users.** One static Go binary (`CGO_ENABLED=0`), sh/PowerShell launchers, and the plugin's mod, which Claude Code runs. No tmux, no AppleScript, no Node/Python.
- **Control flow lives in host code, not in model judgment.** If a step only happens because a model remembered to do it, it is a bug waiting to happen; make a hook or the host do it. No model spawns, wakes, steers or answers for a phase agent.
- **Nothing waits on the human for what baton can decide** (v0.8.3, v0.8.4, v0.8.6). With no deadline, baton waits on them only where they chose it (Pause baton, `/baton pause`, a `max_auto_decisions` they set, a phase agent they stopped twice whose work is not done, while the rest of the run can move: once nothing else can, baton takes the phase back for the lead `escalation_timeout` later) or where nothing in baton can answer (a permission prompt, the usage limit, a login or billing error, a refusal). Every other wait has a deadline whose answer is the model's side, and none is longer than 20 minutes but a block's: a question of baton's at `escalation_timeout` (10 minutes, at most 20; a proposal's own `--wait`, 5 to 20), the lead model's own question where the mod runs, a Wait for me hold after `Timing.HoldLapse` (20 minutes with no word from the human), and a block after `Timing.BlockLook` (30 minutes), when the model looks again for a safe way on and proposes it. An outward proposal (`decide.Outward`) is answered Not now at its deadline (`decide.NotNowRule`): the model does it only if it is safely reversible and stays in the project. A question that never reached the screen is answered by the host's loop (`Loop.lapse`, `hooks.Lapse`). Nothing gives up: retries go on (a crash loop backs off to every 15 minutes), and a stalled session still gets its results and its reminders. A new hold, cap or question needs a deadline that picks the model's side, or an opt-in setting.
- **Hooks fail open.** For Claude Code hooks, exit code 2 means *block*, and so does a Go panic or a `flag` parse error. Every `baton hook` path recovers panics, uses `flag.ContinueOnError` and exits 0 on internal errors; only the deliberate rewake path exits 2. Each hook event has a test proving a panic exits 0, and every hook of the mod has a `.catch` that lets the event through.
- **Dormant unless hosted.** Hooks, the CLI and the mod do nothing unless a live baton host is above the session, apart from `/baton start` handing a plain session over (package `elevate`). `BATON_HOST=1` alone is not enough (v0.8.4): Claude Code's background service passes it on to sessions no host drives. Package `hostcheck` also wants the host's pid, recorded at `.baton/hosts/<instance>.pid`, among the asking process's ancestors, and trusts the variable alone only where processes can't be read. A session that only inherited the variables is told once how to come back (`inherited_notice`), and its `WorktreeCreate` still gets a plain worktree, since baton's hook replaces Claude Code's own; the mod stays dormant, as no host answers its hello.
- **Compaction moves only on proof.** A phase agent's `PreCompact`, `SessionStart(compact)` and `PostCompact` carry no `agent_id` and look like the lead's, so those hooks only log `compact_seen`. A `state.Proof` comes from the mod's report (the lead's compaction) or a new `compact_boundary` in a loop's own transcript.
- **No git operation baton runs, or asks a model to run, rewrites or discards work.** Landing merges the run's branch into a phase's branch and never rebases it: a rebase can drop a resolved conflict without a word, and auto mode may refuse one ([`visible-workers.md`](docs/research/visible-workers.md)). baton's merge starts only on a worktree with nothing uncommitted, and is aborted if it stops.
- **baton types nothing where the mod runs, and never Ctrl-C while an agent may be live.** The mod compacts the lead and submits baton's lines (`bridge.Compact`, `bridge.Submit`) with the human's draft left in the box, and nothing types into a dialog ([spike 35](spikes/35-mod-drives/)). In serial mode v0.7's typing stays (`/compact`, baton's lines), but no digit goes into a dialog: on Claude Code 2.1.30x a Bash prompt's `3` is "Yes, and switch to auto mode" ([spike 39](spikes/39-escape-answers/)), so the host answers its own question by Esc, only while that question is the only dialog open, and records its default itself (`loop/watch.go` `answerOwnQuestion`, `hooks.Lapse`; `auto_answered` with `key: esc`), since no hook reports a dismissal. A draft is cleared only while no agent may be live: one Ctrl-C at the prompt stops every background agent for good, baton's and the model's own.

## Layout

- `cmd/baton/` is the entry point; `internal/<pkg>/` has one package per concern. `decide` owns the escalation policy and every model-facing and human-facing sentence (the band and the board too). `loop.Loop` drives the lead, and `loop.Coordinator` owns the run: phase agents (`fleet.go`, a `loop.Agent` each), the merge queue (`merge.go`), agents' questions (`relay.go`), holds on new agents (`room.go`), retiring (`retire.go`). `state.Project` maps each session to its run (`.baton/runs/<id>/`). `transcript` reads Claude Code's transcripts, read-only and best effort. `machine` and `procs` read the machine and processes without cgo, `ps` or `lsof`, and callers take the reading injected, so no test depends on the machine. `hostcheck` says whether a live host is above the asking process, reading its ancestors one at a time (`procs.Parent`), never the process table; each command keeps its answer (`cli` `IO.Hosted`), and no cache is kept on disk. A session with no plan of its own carries on a run of the same plan file that no live host owns (`cli/carry.go`, `state.Project.Orphans`, `run_carried`).
- **Phase agents** (v0.8, [`visible-workers.md`](docs/research/visible-workers.md)): each phase beside the lead is a `baton:phase` agent of the lead's session, with a sub-run `.baton/runs/<run>/workers/<phase>/` (`Store.Root` its worktree). No code holds two store locks at once. `Dispatch` finds the loop first: an `agent_id` linked to a phase agent is its sub-run, Claude Code's own forks of one change nothing, anything else is the lead's. Learned on real Claude Code 2.1.296:
  - every delivery to an agent is a message, held for its next tool round; a resumed agent gets nothing of `SubagentStart`, so baton's deliveries come at its next tool call or its stop;
  - the type stays offered (Claude Code resumes no agent of a type the session doesn't offer), and `PreToolUse` refuses a model's own call to it;
  - the worktree-isolation guard refuses a quoted command starting with a shell or git, so a phase agent gives a gate as words after `--`, and `PreToolUse` rewrites a quoted one into that form (`gate_as_words`);
  - a hook's `prompt_id` is the session's latest prompt, so a phase's worktree is told from a model's by the open Agent calls (`Runtime.AgentCalls`);
  - `/clear` ends every agent, and baton starts each unfinished phase again (on 2.1.300 it kills an agent's running command, and the agent ends after finishing its turn under the new session id, which `fleet.go`'s `cleared` waits for);
  - in auto mode an agent's end also comes back to the lead as a peer prompt (`<agent-message from="P3">`, then `[Subagent hand-back]`), which the mod drops; `TurnSource` counts that text as a system prompt, never the human's.
  - since 2.1.302, in auto mode, an agent hands its report back with a tool (`SubagentHandback`) that "ends your run" and ends its turn whatever `SubagentStop` says, and one that ends a turn without it is sent back to call it (up to three times); a message still resumes it. So `PreToolUse` decides a phase agent's hand-back as its stop would be decided (`hooks/handback.go`, `handback_refused`): refused with the stop's words while its phase is not reported and nothing it waits on will wake it (counted with the stop's refusals, `MaxStopBlocks`), or to give it a result or a message due first; let through otherwise. `decide.PhaseAgentPrompt` says a hand-back ends only its turn.

  Learned from a real run (v0.8.2): nothing compacts a phase agent, so a sub-run never owes a boundary. A red verification (its gate after `baton done`, or a landing's re-verification) takes the phase up again in place (`state.Retake`, from `settle`, the agent's tick and its stop), and the result goes to the agent. A new agent starts `Fleet.Ramp` (2 minutes) after the newest live one, since the machine's readings lag the load an agent brings. A `verify --here` gate in an agent's worktree holds one of the project's lane slots while it runs (`lane.Job.Here`, with `BATON_LANE` set), so here and lane gates together never exceed the slots; with no `.baton-lane` there is one. A plan change reaches each live agent as a message, once per change to the standing rules or its section (`loop/replan.go`). Since v0.8.6 a phase agent's loop skips the screen gate, since it types nothing (`Loop.agentLine`), and the room log changes only when the kind of room the machine lacks (busy, swapping, memory) changes and has held for `Fleet.RoomSettle` (30 seconds).
- **Phase handles** (v0.8.6, [spike 40](spikes/40-agent-handles/), Claude Code 2.1.301): the mod names each phase agent for its phase (`bridge.Spawn`'s `Name`), and that name is the human's handle on it.
  - **Phase ids are agent names** (`plan/names.go`): 1–32 letters, digits, `_` or `-`, starting with a letter or digit (no dot, `P8b` not `P8.5`); none Claude Code keeps (`main`, `team-lead`, `user`, `system`, in any case), none of an agent id's shape; no two equal ignoring case, since SendMessage falls back to a match ignoring case. `plan.Build` refuses any other with why (the lead's `ExitPlanMode` turns the plan back once, `plan_unbuilt`; an approval or `baton attach` of it attaches nothing, saying why), and so do a replan's draft and a phase the plan file adds; ids the running plan already had pass as they are (`Rebuild`, `Follow`), and a carried run keeps its own. `Plan.Named` is the phase a name addresses, ignoring case.
  - A name points to the latest agent given it (the typeahead, SendMessage by name), so `PreToolUse` refuses a model's own Agent call, the lead's or any agent's, named for one of the run's phases ignoring case while a plan is attached (`decide.AgentNameIsPhase`, `agent_name_refused`, after the `baton:phase` type's refusal); the mod's own spawn (`modCall`) never comes there. baton sends to an agent by its id.
  - **`@<phase> <words>` at the lead's prompt** writes to that phase's agent. Claude Code sends `@name` at the main prompt only to agent-team teammates, so the lead's `UserPromptSubmit` routes it (`hooks/handles.go` `addressed`), by shape alone (the hook's input names no origin): a prompt `TurnSource` takes for the human's, a leading `@<id>` and whitespace, the id one of the run's phases. `state.Addressee` says where the phase stands. For an agent at work (`WorkerWorking`, its `AgentID` in the bridge's `agents.json`, not retiring) the words are queued (`State.ToAgents`, `state.HumanWords`; the same words still queued, once) and the prompt is blocked (`decision: block`, reason `decide.SentToAgent`): no turn, nothing in any request, and the reason, under Claude Code's own frame, is all the human sees (a `systemMessage` beside a block shows nowhere, and `continue: false` lets the words into the conversation: never use either). The coordinator sends them first in each step (`loop/words.go` `toAgents`) through `bridge.Send`, framed as the human's (`decide.HumanToAgent`); the mod's ack takes them off, one unacked is sent again after `sendWait`, and words no agent took (it ended or was stopped first, or Claude Code refused the message) go to the lead as `MessageWords` mail, announced. Claude Code keeps a blocked prompt in the box, where a second Enter sends it again, so `emptyAfter` (1 second) later the mod empties it (`bridge.Empty`), only while it holds exactly that prompt. Every other stand (not started, done, landed, the lead's own, stopped, starting, replaced, landing, retiring) wakes nothing: the prompt goes on to the lead's model with `decide.WordsForLead` as context, and the human gets `decide.WordsToLead`. Each step logs `human_to_agent` (`routed` agent or lead; `step` queued, sent, acked or unsent; `stands` and `why` for the lead).
  - **The retired-agent guard:** the human's typing in an agent's own view wakes it whatever it is, with no hook of the lead's, and an agent whose unchanged worktree Claude Code removed is resumed in the lead's checkout. So every agent baton lets go of for good (`RetireWorker`'s forget, `respawn`, `afresh`) is recorded (`state.Project.LetGo`, a `retired/<agent>` link swept with its run), and the `Handlers` wrapper refuses its every `PreToolUse` (`decide.LetGoRefused`) and lets its other hooks, its stop too, through with nothing recorded; `retired_agent_woke` is logged once per agent, in the lead's run.
- **QA phases** (v0.8.3): a phase with `Type: qa` under its heading (`plan.Phase.Type`, read beside `After:` by `parseHead`) runs the full checks; with `aggregate_qa` on (the default, `BATON_AGGREGATE_QA`), the phases before one are briefed to run focused checks (`brief.qaGuide`, `decide.QAFocus`), and `baton verify` and `baton await` ask once about each job queued before it (`decide.QAAsk`; `--qa` flags an early full check, `qa_early`). A red result there says other phases' work in progress may be why (`plan.QAAhead`), with `baton done --despite-red` for what is not the phase's to fix. A phase agent's narrowed plan keeps the name of its QA phase (`Plan.QAFor`).
- **Plans at approval** (v0.8.5): a plan with one phase heading attaches (`plan.Shaped`); one with none is ordinary plan-mode work and is left alone. `plan.Suggest` makes every anchor occur once in the document (the heading line, else with its line end, else extended by the lines under it) and passes over fenced code, so a plan that quotes its own headings attaches; `plan.Added` reads an anchor's first line. At a hosted lead's `ExitPlanMode`, each once per plan: a plan with phase headings that would not build (`plan.Build`: an id that cannot name an agent, or one equal to another ignoring case, an `After:` naming an unknown or later phase, an anchor that still occurs twice) is turned back with why (`hooks/planbuild.go`, `Runtime.UnbuiltAsked`, `plan_unbuilt`), and the same text again goes on; then the plan's first `ExitPlanMode` is turned back to flag competing instructions (`directives_asked`), and, for a plan that is mostly one chain (`plan.Shape.MostlyChain`: at least `plan.ShapeMinPhases`, 6, phases and a longest chain over `plan.ShapeChainShare`, 0.6, of them), to check each link of that chain against the shape rules (`decide.ShapeCheck`; `directives_asked` gains `phases`, `longest_chain`, `width` and `shape_flagged`). The model may resubmit unchanged, saying in the plan why the chain is real. Every later `ExitPlanMode` of it shows the human its shape in one line (`decide.PlanShape`, `plan_shape`; none for one phase). The shape rules are `decide.ShapeRules` and the skill's `plan` section: keep the two in step, and bump `plan.RulesVersion` when they change (below).
- **The plan moved out of Claude Code's way** (v0.8.6, [spike 38](spikes/38-plan-file-reference/)): after every compaction Claude Code attaches the session's plan-mode file, `<plansDirectory>/<slug>.md`, in full (`plan_file_reference`) for as long as it exists, on top of baton's brief, which quotes what the phase needs of it; in a real run that was about 32k tokens of every phase's starting context, and no setting turns it off. So when a plan baton attaches is that file (`state.Aside`: the slug from the session's transcript, `transcript.Slug`, read before the lock by `Project.LookAside`) and no other live run's plan, baton renames it in its folder to a name from the plan's title (`plan.MoveAside`, `plan.AsideName`: unique, never over a file), follows it there, keeps the old path as `plan_origin` in `plan.json`, and says so (`decide.PlanMoved`; `plan_moved` with `from`, `to` and `by`, or `plan_not_moved` with why). It moves at the hooks' attach, at `baton attach`, and, for a run attached before v0.8.6, before the lead's next compaction that starts a phase, once (`loop.moveAside`, `State.PlanLooked`). An approval of the origin is a revision of the run's plan, since Claude Code writes the session's next plan there, and is moved aside in its turn (`PlanQuestion.Origin`). Carrying a run matches its plan file or its origin.
- **Replans** (v0.8.5, package `replan`): the lead's model restructures the phases not started, in the session; the host decides when, and whether its draft stands. One opens only on a cue, never on a timer or the model's own initiative: the human's `/baton replan ["<what to consider>"]` (`baton replan`, done in that turn), or baton's own at the lead's phase boundary, whose brief comes before the phase's in the same fresh context (`hooks/autoreplan.go`, `replan.Due` and `replan.Auto`): `upgrade` when `State.RulesVersion` is below `plan.RulesVersion` (a run carried across an upgrade) and the phases not started hold a chain, once per rules version; `qa` when a QA phase is under way and the phases not started are mostly one chain, once per QA phase; `marked` once a phase marked `Replan: after` (`plan.Phase.Replan`, read by `parseHead` beside `After:` and `Type:`) is done, once per marked phase. Each cue is settled once, whether a replan opens or not (`State.ReplanCued`, `replan_skipped`). The model edits `.baton/runs/<run>/replan/draft.md` and runs `baton replanned --notes …` (or `--none …`), which checks the draft against what its kind may change (`plan.Redraft`, `replan.LimitsOf`): started and done phases (`state.Frozen`) never change, and the unstarted phases' order and `After:` lines always may. `upgrade` and `qa` change only those (`replan.Structural`), and stand only if the unstarted part's longest chain got shorter or its width grew (`replan.Improved`; otherwise `replan_unchanged`, the plan file untouched); `marked` may also reword and split unstarted phases, never drop or merge them; the human's may also add and reword phases, and drop phases or change the goal sections only as far as their words ask, naming each dropped phase in its notes. A draft that passes is written over the plan file and followed (`plan_replanned`), and recorded as a decision whose undo copies `replan/<n>.md` back (`replan.Restore`, `replan_undone`). Every replan is compared with the approved text, `replan/0.md`, and `baton status` lists each against it. While one is open, or owed at the lead's boundary (`replan.Owed`, `Fleet.AutoReplan`), no new phase agent starts (those at work go on), and the Stop hook leaves the plan file alone; one open for `Timing.ReplanMax` (20 minutes) lapses (`replan_lapsed`) and the plan goes on as it was. `plan.RulesVersion` numbers the planning rules (1 since v0.8.5): a release that changes the shape rules or the skill's planning guidance bumps it, so each run carried across that upgrade gets one structural replan by the new rules. `auto_replan` (on by default; `BATON_AUTO_REPLAN`) turns baton's own replans off; `/baton replan` works either way. Since v0.8.6 the brief also lists, as information only, the pairs of phases not started that could run at once (no `After:` path between them) and name the same file, since they collide when they land (`plan.Paths`, `plan.Plan.Overlaps`, `decide.ReplanBrief.Shared`; `replan_opened` logs `shared`); what a replan may change is the same. The question about a plan approved mid-run is `state.PlanQuestion` (`plan_question_asked`, `_held`, `_resolved`, `_waits`): "replan" names this feature alone. Its options are Wait for me, Start the new plan from P0, then the default third (Continue with the revised plan, or Keep the current run; `decide.PlanQuestionDefault`), so a stray Enter holds the run and lapses into the default, and no single key sets a run's progress aside (v0.8.6).
- **Context valves** (v0.8.6, `internal/valve`, `hooks` `contextValves`, [`context-window.md`](docs/research/context-window.md)): three lines, each a percentage of the limit (the model's window, or the `--autocompact` cap if smaller). At `notice_pct` (60, `BATON_NOTICE_PCT`) the model is told where its context stands and asked nothing (`context_notice`: additional context beside the tool result and a `systemMessage`, never a block; `decide.ContextNotice`); at `checkpoint_pct` (80) it is asked to checkpoint at its next safe point (`context_nudge`), and again at every further tenth; at `warn_pct` (90, never under `valve.WarnFloor`, 200k) the lead's model puts the human the context question (`context_warning`), answered Keep going at `escalation_timeout`. Each fires once a stretch, a later one standing for those before it, and re-arms when the context falls a tenth of the limit below its line; a phase agent gets the notice and the nudge. When any line would come at or after Claude Code's own compaction (`Limits.AutoAt`, `valve.AutoCompactMargin`, 33k, below the limit), every line is its percentage of `AutoAt` instead. With 810k: 486k, 648k and 729k, and Claude Code at 777k. The checkpoint moved from 60 to 80 because a compaction restarts a lead at about 180k: 60% left about 300k of room a stretch, and a real run's lead checkpointed 9 times mid-phase against 7 boundaries. A `checkpoint_pct` set in a config keeps its value.
- **The stall alarm** (v0.8.2, `loop/stall.go`): each loop's watchdog stays quiet while it waits on something that ends by itself, so the coordinator also looks at the run as a whole, about once a minute, with `workers: 0` too. With the plan running, nothing busy and nothing moved for `Timing.StallAfter` (20 minutes), it pushes one notice (`run_stalled`) naming what each phase left waits on. It is not an escalation, which would hold the lead's deliveries, and movement arms it again. Since v0.8.6 a running gate is busy while its log moves (`logMark`: size and modification time) or, with its log still, while its process tree used CPU since the alarm's last look (`Runners.Usage`, read only while the log stands still; no reading leaves the log to decide), as the hung check reads it: only a gate quiet in both is named hung. An `await`, and a gate waiting for a lane, are busy while their runner beats.
- **Pauses and replaced plans** (v0.8.2): a compaction proven while paused covers the one the run owed (`State.Covered`), and `/baton run` keeps it unless the context grew by more than `state.ResumeGrowth` since (`state.Keep`). Attaching while paused stays paused. Before anything replaces or drops a plan, its record is copied into `.baton/runs/<run>/gen-<N>/` (with its replans and its red jobs' logs), and `baton status` lists it.
- **Time saved** (v0.8.6, `state.SavingOf`, `decide.Saved`): at plan completion, the phases' working time against the wall clock from the first phase's start to the last phase's done. A lead phase counts from its start to its done, an agent's from `Worker.Started` to `Worker.Finished` (its sub-run done, set as the merge queue takes it; the landing for older records), not to its landing. The completion line (`decide.PlanDone`) says it for a plan any agent worked on ("phase agents saved about 3h20m: 8h29m of phase work in 5h09m", never below zero), `plan_complete` logs `agent_phases`, `work_seconds`, `wall_seconds` and `saved_seconds`, and `baton status` prints it as `time:` for a complete plan.
- **Locks and writes** (v0.8.5, v0.8.6, `state/lock.go`, `state/store.go`): a store lock (a run's, the project's, a bridge's) is held for the read-modify-write of its small file and nothing else. Run git and other commands, read processes (`procs`, `machine`, `hostcheck`) and transcripts, and call the network before an `Update`, and act on what it decided after it; inside one, take a plan's record with `Store.Record` and `Save` it once the lock is let go (`Store.Archive` is for callers outside a lock). A holder writes its pid, its caller and when it took the lock into the lock file only once it has held it for `holderAfter` (100 ms), and clears only a record it wrote: v0.8.5 wrote and cleared it on every hold, reads included, and on macOS those two writes made a lock and unlock cost 3.8 ms instead of 0.09, which is why its loop tests were slower. A waiter that gives up after 5 seconds logs `lock_timeout` naming the holder, and a hold over a second logs `lock_slow` with its caller. `Store.Update` writes nothing when the state is unchanged, nor does a bridge's update, and `writeAtomic` syncs through `syncFile`: a plain `fsync` on macOS, where Go's `File.Sync` is `F_FULLFSYNC` (milliseconds a call on a busy disk), `File.Sync` elsewhere; the rename stays atomic. Temporary files interrupted writes left (`.<name>.tmp-*`) are removed once a minute old (`state.StaleTemps`, `state.TempAge`) at host start (`Project.Sweep`, `SweepTemps`) and by `baton clean`.
- **A phase's jobs** (v0.8.5): a phase runs one job of each kind at a time, a gate (`verify`) and a wait on something outside (`await`), side by side: `state.QueueJob` replaces only the phase's unfinished job of the same kind. The same check again (`Job.Same`: the command, and for a gate its `--here`) replaces it silently; another command of that kind is refused (`State.Clash`, `refused` with why "another check runs") unless the model passes `--replace`, and `job_queued` names the job it runs `beside`. A phase stands on `State.Standing`, its latest job of each kind: `baton done` leaves it verifying while either runs and is refused while either is red, and `Settle` makes it done once all it waits on passed and reopens it on the first red. `PhaseState.On` records the jobs a verifying or parked phase waits on (`State.WaitsOn`, `HeldOn`); `State.Latest` is only what ran last. A red gate stands until a gate that takes over from it passes (v0.8.6; `State.gate`, `takesOver`): one of the same command, in a lane or `--here`, or one queued with `--replace` (`Job.Replaces`). A narrower check that passes clears nothing (`decide.NotCleared`); `baton verify` of another command over a red gate says so (`decide.RedGateStands`, `red_gate` on `job_queued`), and with `--replace` records a decision the human is told of (`decide.GateReplaced`, `replaces_gate`). `baton done` names the command that must pass (`decide.RedRefusal`), and `--despite-red` is unchanged. A job's result lists the failure lines of its whole log before the tail (`lane.ReadExcerpt`, `lane.Failure`, via `hooks.JobLog`: at most 20, each clipped), and a red job's log is never pruned (`State.KeptLogs`, `pruneLogs`) and goes with the plan's record into `gen-<N>/jobs/`. (v0.8.4 shipped a regression its own full e2e gate had caught: the tail showed only the last failure, a one-test `-run` gate stood in for the red one, and the log was pruned.)
- **The model's own background work** (v0.8.5, `hooks/background.go`): a tool call that starts it (a Bash or PowerShell result with a `backgroundTaskId`, a Monitor's `taskId`, an Agent or workflow launched `async_launched`) gets baton's reminder with its result (`Words.BackgroundStarted`), its id goes to `Runtime.BackgroundTold`, and `background_told` is logged with `via: start`, in a phase agent's sub-run too. The Stop refusal over background work is the fallback, for work whose start baton did not see (`Runtime.Untold`). Claude Code lists every background task of the session at each `Stop` and `SubagentStop`, whoever started it, so a loop's stop leaves out the work another loop of the run was told of as it started (`state.Store.OthersTold`, read before the lock). Both tell the model never to start a loop or another background task only to wait for one, since Claude Code wakes it when that ends (`decide.meanwhile`, v0.8.6): a real run's lead had started such pollers.
- **`baton clean`** (`cli/cleancmd.go`) ends only what is baton's: a process carrying a gone session's `BATON_INSTANCE` is stopped when it works under baton's home, listed with the command to stop it when it works in the project, a worktree on record or a lane, and left alone anywhere else, or where its directory can't be read (a gpg-agent or ssh-agent a hosted shell started, in `/` or the home directory).
- **Retiring** (v0.6): `State.Generation` counts a run's plans, and `loop.RetireWorker` ends an agent from any baton process, marking `Worker.Retiring` under the run's lock first. With `workers: 0` (`Coordinator.Fleet` nil) and none on record, baton behaves as v0.4 did, apart from the mod's compactions and the stall alarm; keep it that way.
- **Recovery** (v0.7, [`recovery.md`](docs/research/recovery.md)): a refused turn is never retried; a rewind never rolls baton's record back; a crashed lead comes back (`internal/cli/recover.go`); `state.HereGate` holds edits and landings while a `verify --here` gate runs. Since v0.8.4 the host never gives up on a crash loop: past `state.MaxRecoveries` in `state.RecoveryWindow` it tries again after `Timing.RecoverAfter` (5 minutes), then every `RecoverEvery` (15). An API error a fresh context avoids (`state.StopError.Afresh`: prompt too long, a request too large, a broken tool history) starts the lead (`loop/afresh.go`) or a phase agent (`Coordinator.erred`) afresh from its brief, with the same backoff; refusals, logins, billing and an unknown model stay the human's.
- **Stuck edges** (v0.8.4): a verify job whose log has not grown and whose process tree used no CPU for `Timing.HungAfter` (20 minutes) is stopped as unverified (`loop/jobs.go` `hung`, `procs.TreeUsage`; never on log silence alone, so a platform that can't read CPU never stops one). A landing held by the lead's overlapping uncommitted files mails the lead to commit them by path after `Timing.LandNudge` (10 minutes); one held by a checkout off the run's branch is pushed once. A phase agent the human stopped (`loop/stopped.go`, `state.Worker.Stops`) is asked about on the lead's screen; at `escalation_timeout` baton decides from the record (`state.Satisfied`): work done lets the agent go and lands it, otherwise a first stop restarts it and tells the human, and a second takes it down and asks with no deadline while the rest of the run can move (the question steps aside after `escalation_timeout`, and comes back when the human writes). Since v0.8.6, once nothing else can (`state.Moves`: no phase can start, no other agent at work, the lead idle with no job, compaction or replan under way), the host marks the moment (`Relay.Stuck`), and `escalation_timeout` later (`state.TakeUpAt`, never before the question's own deadline) closes the question, retires the agent (`RetireWorker`, which puts the phase back), and the lead takes the phase up at a boundary, its brief quoting why and where the agent's work is (`decide.StoppedTakenBrief`: merge its branch, never rebase). It is a decision with `/baton pause` as its undo, announced, pushed and logged (`stopped_phase_taken`); until then the lead's stop with no phase in hand names the phase and when (`stopped_phase_waits`), and the human's answer wins. Where the mod runs, a phase agent's permission prompt holds only that agent (`Loop.dialogHolds`, `state.Dialog.Phase`; spike 36), while serial mode holds on every dialog, since a typed key would answer the agent's prompt.
- **The mod** (`plugin/hooks/baton.js`) is a thin executor: it spawns and messages phase agents, asks the human, compacts the lead and submits baton's lines to it, empties the lead's input box of a prompt baton sent on to a phase agent, drops agents' reports before the lead's model sees them, draws the band, and reports what it sees; it decides and words nothing. It asks from its band's render hook, never its timer, and its `tool.call` hook settles baton's questions, and the lead model's own (`hooks.Bound`: its Recommended option, else its first), at their deadline ([spike 34](spikes/34-ask-deadline/)); serial mode leaves the model's own questions to the human. The host asks for the lead's compaction once its Stop hook has run, a moment before Claude Code counts the turn over, so the mod holds a compaction Claude Code declines while the lead's turn runs (by the mod's own `turn.start` and `turn.complete`) and calls it from that turn's `turn.complete`, once ([spike 37](spikes/37-compact-at-turn-end/)); past `HOLD_MS` (30 seconds, within the host's `modAckWait`) it acks the refusal, and the host asks again after the turn (`loop.redo`). Run `make mod-test` and `claude plugin validate plugin` before committing a change to it, and never edit it while a session that loaded it runs.
- **The bridge** (`internal/bridge`): numbered command files under `.baton/runs/<run>/mod/`, each for one host instance, and reports through `baton mod report`, each recorded once. A report of the lead's compaction (the ack of a compact command, compacting, compacted) is counted in the run's state before the bridge records it (v0.8.6, `cli/modcmd.go` `compactionFirst`, `state.CountOnce` with `Runtime.ModCounted`), so a report process killed between the two leaves the report with the mod, which sends it again, and it counts once; the bridge's record is read there without its lock (`Bridge.Peek`), so a report waits on two locks at most, and the mod gives a report and `baton board` 15 seconds (`REPORT_TIMEOUT_MS`, `VIEW_TIMEOUT_MS`), above two lock waits. No hello from the mod, or one in another `bridge.Protocol`, means a serial run (`loop/mod.go`); after a restart of a run whose mod said hello, the host waits up to `Timing.ModHello` for the new claude's mod before it gives the session anything. When the host drives another run (a carried run, `Loop.drive`), it issues `bridge.Moved` in the old run's bridge; the mod says hello on the new one and starts its command count afresh, since the count is per run.
- `plugin/` is the Claude Code plugin: the skill, the launchers, the Stop hook that finishes `/baton start`, and the mod. `SKILL.md` is a stub that loads `internal/skill/skill.md` from the binary, so edit that, and never put `$ARGUMENTS` in the stub's inline command ([spike 18](spikes/18-skill-inject/)). `.claude-plugin/marketplace.json` makes this repo its own marketplace.
- `spikes/` holds archived experiments. Don't import from them.

## Commands

```sh
make build      # ./dist/baton for this machine
make test       # unit tests
make mod-test   # baton's mod under Claude Code's test kit (needs claude; calls no model)
make cross      # all release targets into ./dist
make e2e        # real-claude scenarios (needs BATON_E2E=1, costs a few cents)
make release-prep VERSION=v0.1.0   # pin checksums + plugin version, then commit and tag
```

End-to-end tests run real `claude --model haiku` and assert on `events.jsonl` and hook logs, never the screen. Each session has its own `BATON_HOME` and `GNUPGHOME` and loads this repository's plugin with `--plugin-dir` (`noModPlugin` for serial mode). The harness sets `BATON_WORKERS=0` unless a scenario calls `StartAgents`, `BATON_TEST_LOAD=0`, and `BATON_AGENT_RAMP=5s` (phase agents start 2 minutes apart otherwise); `BATON_ABANDON_AFTER` shortens the wait before a run counts as abandoned, and `BATON_HOLD_LAPSE`, `BATON_BLOCK_LOOK`, `BATON_RECOVER_AFTER`, `BATON_RECOVER_EVERY` and `BATON_REPLAN_MAX` the holds, blocks, crash backoff and replans. `BATON_AUTO_REPLAN=0` keeps baton's own replans out of a scenario that would cue one. `BATON_NOTICE_PCT` and `BATON_CHECKPOINT_PCT` move the context valves (`0` turns one off; with a small `--autocompact` cap every line moves before Claude Code's own compaction), and `BATON_WARN_TOKENS` sets the context question's line. Plan mode writes into `~/.claude/plans` unless the scratch project sets `plansDirectory`, so every scenario that plans calls `PlansHere`, which sets it to `plans/` inside the project and keeps that folder and the settings file out of git. `Session.ApprovePermissions` stands in for the human on the model's own permission prompts only, leaving every question of baton's to its deadline. Allow rules name the exact command, since auto mode drops a broad one like `Bash(sh:*)`. `BATON_E2E_SONNET=1` adds the Sonnet scenarios. Run one `go test` process at a time: the mod's store file in `~/.claude` is shared. The sessions take the permission mode from your own Claude Code settings, so in auto mode agents' ends come back as hand-backs the mod drops (`mod_dropped`). Claude Code's Bash tool ends a foreground command after 2 minutes unless the model sets a timeout, so a scenario's plan that waits longer asks for one (`BATON_FOREGROUND_MAX` takes at most 10m).

## Conventions

- Go: standard library first; a new dependency needs a reason (current: `creack/pty`, `golang.org/x/term`, `golang.org/x/sys`, `gofrs/flock`).
- Commits: [Conventional Commits](https://www.conventionalcommits.org/), one coherent unit per commit, so `git log` reads as the story of the project.
- Tests: table-driven, next to the code; time-dependent logic takes an injected clock; no test provokes a refusal.
- Every user-visible action baton takes is announced in the session (`systemMessage` or the band) and logged to `events.jsonl`.
