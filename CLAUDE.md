# Working on baton

baton runs a multi-phase Claude Code plan unattended by hosting `claude` in a pseudo-terminal it owns. The design is in `docs/plan.md`, and how a run reaches the human (note, propose, blocked; snapshots; answering its own question) is in `docs/escalation.md`. The evidence behind them is in `docs/research/` (`spikes.md`, `reliability.md`, `escalation.md`, `sessions.md` for plan approval and how runs map to sessions, `parallel.md` for the dependency graph, jobs, lanes and switching between phases, `workers.md` for worker sessions, landing their work under a live session, and relaying their questions, and `recovery.md` for refusals, rewinds and a crashed claude). Read them before changing how compaction, escalation, hooks, jobs, workers, or the host loop work: several obvious-looking alternatives were tested and **do not work** (e.g. changing `autoCompactWindow` mid-session, scheduling `/compact` with CronCreate).

## Non-negotiables

- **The live terminal stays visible.** baton is a byte-for-byte passthrough; nothing may draw over or replace the Claude Code TUI.
- **No runtime dependencies for users.** One static Go binary (`CGO_ENABLED=0`), plus sh/PowerShell launchers. No tmux, no AppleScript, no Node/Python at runtime.
- **Control flow lives in host code, not in model judgment.** If a step only happens because the model remembered to do it, it is a bug waiting to happen; make a hook or the host do it.
- **Hooks fail open.** For Claude Code hooks, exit code 2 means *block*. A Go panic or a `flag` parse error also exits 2. Every `baton hook` path recovers panics, uses `flag.ContinueOnError`, and exits 0 on internal errors; only the deliberate rewake path exits 2. Each hook event has a test proving a panic exits 0.
- **Dormant unless hosted.** Anything that runs inside a session (hooks, CLI) does nothing unless `BATON_HOST=1` is set, apart from `/baton start` handing a plain session over (package `elevate`).

## Layout

- `cmd/baton/` — entry point and subcommand router.
- `internal/<pkg>/` — one package per concern (cli, config, host, pty, loop, hooks, decide, gitx, plan, state, brief, lane, valve, statusline, board, notify, elevate, upgrade, skill, machine, procs, transcript). `decide` owns the escalation policy and every model-facing sentence about it, and the words of baton's band and board; `board` is baton's view of a run (the plan's steps, each phase, the lead), which the mod draws from `baton board`; `gitx.Usable` is the one test for whether git applies; `state.Project` maps each Claude Code session to its own run (`.baton/runs/<id>/`), and everything inside a session finds its run by session id; `lane` runs a job's command on a commit in a worktree outside the checkout (through the project's `.baton-lane`), started by the host as a detached `baton lane-run` so it outlives claude and a restart; `machine` reads the CPUs, memory and load (sysctl on macOS, `/proc` and cgroups on Linux) and `procs` this user's processes (`baton clean`), both without cgo, `ps` or `lsof`, and code that uses them takes the reading or the table injected (`cli.IO.Machine`, `hooks.Deps.Machine`, the process table of `baton clean`'s cleaner), so no test depends on the machine it runs on.
- Workers (v0.5, phase agents since v0.8): `host.Run` runs the lead session in the human's terminal; `loop.Coordinator` ticks the lead's `loop.Loop` and owns what belongs to the run (`fleet.go` starts, ends and takes up again the phase agents, each with a `loop.Agent` of its own, `merge.go` lands their branches, `relay.go` has the mod put their questions to the human and applies the answers, plus usage limits and the upgrade restart). A worker is a sub-run of the lead's run (`.baton/runs/<run>/workers/<phase>/`, ref `<run>/<phase>`): `Store.Root` is its worktree, `Store.Checkout` the human's checkout and `Store.Project` the main `.baton`. No code holds two store locks at once.
- Ending workers (v0.6): `State.Generation` counts the plans attached to a run and each worker records its own, since plans reuse phase ids; a worker of an older plan is retired before anything else. `loop.RetireWorker` (`retire.go`) ends a worker from any baton process (the run's coordinator, the new-run sweep when a plan is attached, `baton clean`): it marks the roster entry (`Worker.Retiring`) under the run's lock first, so a worker is never resumed and retired at once, and one whose sub-run's owner is live is left alone. `state.Abandoned` is the one test for a run no session will come back to. With `workers: 0`, or `auto` on a machine with room for none, there is no fleet (`Coordinator.Fleet` is nil), and the coordinator only retires the workers its run has on record; with none on record, baton behaves exactly as v0.4 did; keep it that way. `workers: auto` sizes the fleet from `machine` (`config.AutoWorkers`), and `loop/room.go` holds new workers back (the machine, lanes, conflicts, usage); every hold is host code, never model judgment.
- Recovery (v0.7, `docs/research/recovery.md`): `internal/transcript` reads Claude Code's transcript, read-only and best effort (any error leaves baton as it was), to tell a refusal apart at `StopFailure` (`Refusal`) and to notice a rewind: `UserPromptSubmit` marks the last entry (`Run.Mark`, from `Leaf`), and the turn's next hook checks the prompt descends from it (`Fork`, `internal/hooks/rewind.go`). A refused turn escalates `refused`; baton never retries it, types nothing into that conversation, and starts no fresh one by itself. A rewind never rolls baton's record back; the model is told what still stands (`decide.Rewound`). A conversation cleared mid-phase gets `brief.Fresh`. A lead whose claude exits by itself mid-plan is brought back by its host (`internal/cli/recover.go`: `recoverable` reads `host.Exit.By`; an exec as the upgrade restart does, `BATON_RECOVER`, at most 2 in 30 minutes in `Run.Recoveries`, a fresh session once per phase via `Project.Link`). `state.HereGate` is the lead's or a worker's `verify --here` gate: while it runs, edits there are refused, the session is not switched, and nothing lands in the checkout. The merge queue (`loop/merge.go`) verifies a landing again for any other landing in between, but at most once for the checkout's own commits (`state.Job.Requeue`, `Coordinator.moved`).
- Phase agents (v0.8, in progress; `docs/research/visible-workers.md`): `plugin/hooks/baton.js` is baton's mod, JavaScript Claude Code runs in the lead's claude. It is a thin executor: it spawns and messages `baton:phase` agents, asks the human, keeps those agents' reports from the lead's model, and reports what it sees; it decides and words nothing. It asks baton's questions from its band's render hook (never from its timer: it would not see its own call), and its `tool.call` hook bounds each of baton's questions in the lead's session, the lead model's own included, by what `baton mod report` answers (`hooks.Bound`), answering the call itself at the deadline, which fires no `PostToolUse` (`hooks.Settle` records it); nothing types into a dialog where the mod runs ([spike 34](spikes/34-ask-deadline/)). `internal/bridge` is how the host and the mod talk: numbered command files under `.baton/runs/<run>/mod/`, each for one host instance, and numbered reports through `baton mod report`, each recorded once. With no hello from the mod while a plan runs, the run is serial (`loop/mod.go`). `make mod-test` validates the mod and runs its tests (`test/mod/`) under Claude Code's own test kit; never edit the mod while a session that loaded it runs.
- `plugin/` — the Claude Code plugin (skill, launchers, the Stop hook that finishes `/baton start`, the mod). Its `SKILL.md` is a stub that loads the instructions from the binary (`baton skill`, from `internal/skill/skill.md`), so edit those, not the stub; and never put `$ARGUMENTS` in the stub's inline command, which Claude Code substitutes before the shell runs it ([spike 18](spikes/18-skill-inject/)). `.claude-plugin/marketplace.json` at the repo root makes this repo its own marketplace.
- `spikes/` — archived throwaway experiments. Not maintained; don't import from them.

## Commands

```sh
make build      # ./dist/baton for this machine
make test       # unit tests
make mod-test   # baton's mod under Claude Code's test kit (needs claude; calls no model)
make cross      # all release targets into ./dist
make e2e        # real-claude scenarios (needs BATON_E2E=1, costs a few cents)
make release-prep VERSION=v0.1.0   # pin checksums + plugin version, then commit and tag
```

End-to-end tests run real `claude --model haiku`. They approve dialogs with `AutoApprove`, or, where a proposal is on screen, use `acceptEdits` and narrow allow rules (AutoApprove's Enter would pick option 1). That keeps them independent of the permission mode: Haiku had no auto mode when they were written, and Haiku 5.5 has it ([spike 19](spikes/19-background-work/)). Every session gets its own `BATON_HOME` and `GNUPGHOME`, so neither your baton config nor your keyring is ever touched, and the signing tests use stand-in gpg scripts. Tests never notify, and they remove any plan file plan mode writes to `~/.claude/plans`. The harness sets `BATON_WORKERS=0` unless a scenario starts workers (`StartWorkers`). One more variable is for tests only: `BATON_ABANDON_AFTER` shortens the two minutes a run must have been quiet before baton takes it for abandoned (`state.Abandoned`: the sweep when a new run starts, and `baton clean`). In auto mode Claude Code drops a broad allow rule like `Bash(sh:*)`, and its classifier may then deny the command, so a scenario that allows a command names it exactly (`Bash(sh slow.sh)`). `BATON_E2E_SONNET=1` adds the Sonnet scenarios: auto mode at a phase boundary, and the replay of the signing outage behind graduated escalation ([`docs/escalation.md`](docs/escalation.md)).

## Conventions

- Go: standard library first; a new dependency needs a reason (current: `creack/pty`, `golang.org/x/term`, `golang.org/x/sys`, `gofrs/flock`).
- Commits: [Conventional Commits](https://www.conventionalcommits.org/) (`feat(host): …`, `fix(hooks): …`, `docs: …`), one coherent unit per commit, so `git log` reads as the story of the project.
- Tests: table-driven unit tests next to the code; time-dependent logic takes an injected clock.
- End-to-end tests assert on `.baton/runs/*/events.jsonl` and hook logs, never on screen contents.
- Every user-visible action baton takes is announced in the session (`systemMessage`) and logged to `events.jsonl`.
