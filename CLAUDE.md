# Working on baton

baton runs a multi-phase Claude Code plan unattended by hosting `claude` in a pseudo-terminal it owns. The design is [`docs/design.md`](docs/design.md). The evidence is in `docs/research/`, one file per question, each with a summary at its top. Read the one that applies before changing compaction, escalation, hooks, jobs, phase agents or the host loop: several obvious-looking alternatives were tested and **do not work** (changing `autoCompactWindow` mid-session, scheduling `/compact` with CronCreate, hiding baton's agent type from the session).

## Non-negotiables

- **The live terminal stays visible.** baton is a byte-for-byte passthrough; nothing may draw over or replace the Claude Code TUI.
- **No runtime dependencies for users.** One static Go binary (`CGO_ENABLED=0`), sh/PowerShell launchers, and the plugin's mod, which Claude Code runs. No tmux, no AppleScript, no Node/Python.
- **Control flow lives in host code, not in model judgment.** If a step only happens because a model remembered to do it, it is a bug waiting to happen; make a hook or the host do it. No model spawns, wakes, steers or answers for a phase agent.
- **Nothing waits on the human for what baton can decide** (v0.8.3, v0.8.4). With no deadline, baton waits on them only where they chose it (Pause baton, `/baton pause`, a `max_auto_decisions` they set, a phase agent they stopped twice whose work is not done) or where nothing in baton can answer (a permission prompt, the usage limit, a login or billing error, a refusal). Every other wait has a deadline whose answer is the model's side, and none is longer than 20 minutes but a block's: a question of baton's at `escalation_timeout` (10 minutes, at most 20; a proposal's own `--wait`, 5 to 20), the lead model's own question where the mod runs, a Wait for me hold after `Timing.HoldLapse` (20 minutes with no word from the human), and a block after `Timing.BlockLook` (30 minutes), when the model looks again for a safe way on and proposes it. An outward proposal (`decide.Outward`) is answered Not now at its deadline (`decide.NotNowRule`): the model does it only if it is safely reversible and stays in the project. A question that never reached the screen is answered by the host's loop (`Loop.lapse`, `hooks.Lapse`). Nothing gives up: retries go on (a crash loop backs off to every 15 minutes), and a stalled session still gets its results and its reminders. A new hold, cap or question needs a deadline that picks the model's side, or an opt-in setting.
- **Hooks fail open.** For Claude Code hooks, exit code 2 means *block*, and so does a Go panic or a `flag` parse error. Every `baton hook` path recovers panics, uses `flag.ContinueOnError` and exits 0 on internal errors; only the deliberate rewake path exits 2. Each hook event has a test proving a panic exits 0, and every hook of the mod has a `.catch` that lets the event through.
- **Dormant unless hosted.** Hooks, the CLI and the mod do nothing unless a live baton host is above the session, apart from `/baton start` handing a plain session over (package `elevate`). `BATON_HOST=1` alone is not enough (v0.8.4): Claude Code's background service passes it on to sessions no host drives. Package `hostcheck` also wants the host's pid, recorded at `.baton/hosts/<instance>.pid`, among the asking process's ancestors, and trusts the variable alone only where processes can't be read. A session that only inherited the variables is told once how to come back (`inherited_notice`), and its `WorktreeCreate` still gets a plain worktree, since baton's hook replaces Claude Code's own; the mod stays dormant, as no host answers its hello.
- **Compaction moves only on proof.** A phase agent's `PreCompact`, `SessionStart(compact)` and `PostCompact` carry no `agent_id` and look like the lead's, so those hooks only log `compact_seen`. A `state.Proof` comes from the mod's report (the lead's compaction) or a new `compact_boundary` in a loop's own transcript.
- **No git operation baton runs, or asks a model to run, rewrites or discards work.** Landing merges the run's branch into a phase's branch and never rebases it: a rebase can drop a resolved conflict without a word, and auto mode may refuse one ([`visible-workers.md`](docs/research/visible-workers.md)). baton's merge starts only on a worktree with nothing uncommitted, and is aborted if it stops.
- **baton types nothing where the mod runs, and never Ctrl-C while an agent may be live.** The mod compacts the lead and submits baton's lines (`bridge.Compact`, `bridge.Submit`) with the human's draft left in the box, and nothing types into a dialog ([spike 35](spikes/35-mod-drives/)). In serial mode v0.7's typing stays (`/compact`, baton's lines, a typed `3` only while baton's question is the only dialog open), but a draft is cleared only while no agent may be live: one Ctrl-C at the prompt stops every background agent for good, baton's and the model's own.

## Layout

- `cmd/baton/` is the entry point; `internal/<pkg>/` has one package per concern. `decide` owns the escalation policy and every model-facing and human-facing sentence (the band and the board too). `loop.Loop` drives the lead, and `loop.Coordinator` owns the run: phase agents (`fleet.go`, a `loop.Agent` each), the merge queue (`merge.go`), agents' questions (`relay.go`), holds on new agents (`room.go`), retiring (`retire.go`). `state.Project` maps each session to its run (`.baton/runs/<id>/`). `transcript` reads Claude Code's transcripts, read-only and best effort. `machine` and `procs` read the machine and processes without cgo, `ps` or `lsof`, and callers take the reading injected, so no test depends on the machine. `hostcheck` says whether a live host is above the asking process, reading its ancestors one at a time (`procs.Parent`), never the process table; each command keeps its answer (`cli` `IO.Hosted`), and no cache is kept on disk. A session with no plan of its own carries on a run of the same plan file that no live host owns (`cli/carry.go`, `state.Project.Orphans`, `run_carried`).
- **Phase agents** (v0.8, [`visible-workers.md`](docs/research/visible-workers.md)): each phase beside the lead is a `baton:phase` agent of the lead's session, with a sub-run `.baton/runs/<run>/workers/<phase>/` (`Store.Root` its worktree). No code holds two store locks at once. `Dispatch` finds the loop first: an `agent_id` linked to a phase agent is its sub-run, Claude Code's own forks of one change nothing, anything else is the lead's. Learned on real Claude Code 2.1.296:
  - every delivery to an agent is a message, held for its next tool round; a resumed agent gets nothing of `SubagentStart`, so baton's deliveries come at its next tool call or its stop;
  - the type stays offered (Claude Code resumes no agent of a type the session doesn't offer), and `PreToolUse` refuses a model's own call to it;
  - the worktree-isolation guard refuses a quoted command starting with a shell or git, so a phase agent gives a gate as words after `--`, and `PreToolUse` rewrites a quoted one into that form (`gate_as_words`);
  - a hook's `prompt_id` is the session's latest prompt, so a phase's worktree is told from a model's by the open Agent calls (`Runtime.AgentCalls`);
  - `/clear` ends every agent, and baton starts each unfinished phase again (on 2.1.300 it kills an agent's running command, and the agent ends after finishing its turn under the new session id, which `fleet.go`'s `cleared` waits for);
  - in auto mode an agent's end also comes back to the lead as a peer prompt (`<agent-message from="P3">`, then `[Subagent hand-back]`), which the mod drops; `TurnSource` counts that text as a system prompt, never the human's.

  Learned from a real run (v0.8.2): nothing compacts a phase agent, so a sub-run never owes a boundary. A red verification (its gate after `baton done`, or a landing's re-verification) takes the phase up again in place (`state.Retake`, from `settle`, the agent's tick and its stop), and the result goes to the agent. A new agent starts `Fleet.Ramp` (2 minutes) after the newest live one, since the machine's readings lag the load an agent brings. A `verify --here` gate in an agent's worktree holds one of the project's lane slots while it runs (`lane.Job.Here`, with `BATON_LANE` set), so here and lane gates together never exceed the slots; with no `.baton-lane` there is one. A plan change reaches each live agent as a message, once per change to the standing rules or its section (`loop/replan.go`).
- **QA phases** (v0.8.3): a phase with `Type: qa` under its heading (`plan.Phase.Type`, read beside `After:` by `parseHead`) runs the full checks; with `aggregate_qa` on (the default, `BATON_AGGREGATE_QA`), the phases before one are briefed to run focused checks (`brief.qaGuide`, `decide.QAFocus`), and `baton verify` and `baton await` ask once about each job queued before it (`decide.QAAsk`; `--qa` flags an early full check, `qa_early`). A red result there says other phases' work in progress may be why (`plan.QAAhead`), with `baton done --despite-red` for what is not the phase's to fix. A phase agent's narrowed plan keeps the name of its QA phase (`Plan.QAFor`).
- **Plans at approval** (v0.8.5): a plan with one phase heading attaches (`plan.Shaped`); one with none is ordinary plan-mode work and is left alone. `plan.Suggest` makes every anchor occur once in the document (the heading line, else with its line end, else extended by the lines under it) and passes over fenced code, so a plan that quotes its own headings attaches; `plan.Added` reads an anchor's first line. At a hosted lead's `ExitPlanMode`, each once per plan: a plan with phase headings that would not build (`plan.Build`: a duplicate id, an `After:` naming an unknown or later phase, an anchor that still occurs twice) is turned back with why (`hooks/planbuild.go`, `Runtime.UnbuiltAsked`, `plan_unbuilt`), and the same text again goes on; then the plan's first `ExitPlanMode` is turned back to flag competing instructions (`directives_asked`), and, for a plan that is mostly one chain (`plan.Shape.MostlyChain`: at least `plan.ShapeMinPhases`, 6, phases and a longest chain over `plan.ShapeChainShare`, 0.6, of them), to check each link of that chain against the shape rules (`decide.ShapeCheck`; `directives_asked` gains `phases`, `longest_chain`, `width` and `shape_flagged`). The model may resubmit unchanged, saying in the plan why the chain is real. Every later `ExitPlanMode` of it shows the human its shape in one line (`decide.PlanShape`, `plan_shape`; none for one phase). The shape rules are `decide.ShapeRules` and the skill's `plan` section: keep the two in step, and bump `plan.RulesVersion` when they change (below).
- **Replans** (v0.8.5, package `replan`): the lead's model restructures the phases not started, in the session; the host decides when, and whether its draft stands. One opens only on a cue, never on a timer or the model's own initiative: the human's `/baton replan ["<what to consider>"]` (`baton replan`, done in that turn), or baton's own at the lead's phase boundary, whose brief comes before the phase's in the same fresh context (`hooks/autoreplan.go`, `replan.Due` and `replan.Auto`): `upgrade` when `State.RulesVersion` is below `plan.RulesVersion` (a run carried across an upgrade) and the phases not started hold a chain, once per rules version; `qa` when a QA phase is under way and the phases not started are mostly one chain, once per QA phase; `marked` once a phase marked `Replan: after` (`plan.Phase.Replan`, read by `parseHead` beside `After:` and `Type:`) is done, once per marked phase. Each cue is settled once, whether a replan opens or not (`State.ReplanCued`, `replan_skipped`). The model edits `.baton/runs/<run>/replan/draft.md` and runs `baton replanned --notes …` (or `--none …`), which checks the draft against what its kind may change (`plan.Redraft`, `replan.LimitsOf`): started and done phases (`state.Frozen`) never change, and the unstarted phases' order and `After:` lines always may. `upgrade` and `qa` change only those (`replan.Structural`), and stand only if the unstarted part's longest chain got shorter or its width grew (`replan.Improved`; otherwise `replan_unchanged`, the plan file untouched); `marked` may also reword and split unstarted phases, never drop or merge them; the human's may also add and reword phases, and drop phases or change the goal sections only as far as their words ask, naming each dropped phase in its notes. A draft that passes is written over the plan file and followed (`plan_replanned`), and recorded as a decision whose undo copies `replan/<n>.md` back (`replan.Restore`, `replan_undone`). Every replan is compared with the approved text, `replan/0.md`, and `baton status` lists each against it. While one is open, or owed at the lead's boundary (`replan.Owed`, `Fleet.AutoReplan`), no new phase agent starts (those at work go on), and the Stop hook leaves the plan file alone; one open for `Timing.ReplanMax` (20 minutes) lapses (`replan_lapsed`) and the plan goes on as it was. `plan.RulesVersion` numbers the planning rules (1 since v0.8.5): a release that changes the shape rules or the skill's planning guidance bumps it, so each run carried across that upgrade gets one structural replan by the new rules. `auto_replan` (on by default; `BATON_AUTO_REPLAN`) turns baton's own replans off; `/baton replan` works either way. The question about a plan approved mid-run is `state.PlanQuestion` (`plan_question_asked`, `_held`, `_resolved`, `_waits`): "replan" names this feature alone.
- **The stall alarm** (v0.8.2, `loop/stall.go`): each loop's watchdog stays quiet while it waits on something that ends by itself, so the coordinator also looks at the run as a whole, about once a minute, with `workers: 0` too. With the plan running, nothing busy and nothing moved for `Timing.StallAfter` (20 minutes), it pushes one notice (`run_stalled`) naming what each phase left waits on. It is not an escalation, which would hold the lead's deliveries, and movement arms it again.
- **Pauses and replaced plans** (v0.8.2): a compaction proven while paused covers the one the run owed (`State.Covered`), and `/baton run` keeps it unless the context grew by more than `state.ResumeGrowth` since (`state.Keep`). Attaching while paused stays paused. Before anything replaces or drops a plan, its record is copied into `.baton/runs/<run>/gen-<N>/` (with its replans), and `baton status` lists it.
- **Locks** (v0.8.5, `state/lock.go`): a store lock (a run's, the project's, a bridge's) is held for the read-modify-write of its small file and nothing else. Run git and other commands, read processes (`procs`, `machine`, `hostcheck`) and transcripts, and call the network before an `Update`, and act on what it decided after it; inside one, take a plan's record with `Store.Record` and `Save` it once the lock is let go (`Store.Archive` is for callers outside a lock). The holder writes its pid, its caller and when it took the lock into the lock file; a waiter that gives up after 5 seconds logs `lock_timeout` naming them, and a hold over a second logs `lock_slow` with its caller.
- **A phase's jobs** (v0.8.5): a phase runs one job of each kind at a time, a gate (`verify`) and a wait on something outside (`await`), side by side: `state.QueueJob` replaces only the phase's unfinished job of the same kind. The same check again (`Job.Same`: the command, and for a gate its `--here`) replaces it silently; another command of that kind is refused (`State.Clash`, `refused` with why "another check runs") unless the model passes `--replace`, and `job_queued` names the job it runs `beside`. A phase stands on `State.Standing`, its latest job of each kind: `baton done` leaves it verifying while either runs and is refused while either is red, and `Settle` makes it done once all it waits on passed and reopens it on the first red. `PhaseState.On` records the jobs a verifying or parked phase waits on (`State.WaitsOn`, `HeldOn`); `State.Latest` is only what ran last.
- **The model's own background work** (v0.8.5, `hooks/background.go`): a tool call that starts it (a Bash or PowerShell result with a `backgroundTaskId`, a Monitor's `taskId`, an Agent or workflow launched `async_launched`) gets baton's reminder with its result (`Words.BackgroundStarted`), its id goes to `Runtime.BackgroundTold`, and `background_told` is logged with `via: start`, in a phase agent's sub-run too. The Stop refusal over background work is the fallback, for work whose start baton did not see (`Runtime.Untold`).
- **`baton clean`** (`cli/cleancmd.go`) ends only what is baton's: a process carrying a gone session's `BATON_INSTANCE` is stopped when it works under baton's home, listed with the command to stop it when it works in the project, a worktree on record or a lane, and left alone anywhere else, or where its directory can't be read (a gpg-agent or ssh-agent a hosted shell started, in `/` or the home directory).
- **Retiring** (v0.6): `State.Generation` counts a run's plans, and `loop.RetireWorker` ends an agent from any baton process, marking `Worker.Retiring` under the run's lock first. With `workers: 0` (`Coordinator.Fleet` nil) and none on record, baton behaves as v0.4 did, apart from the mod's compactions and the stall alarm; keep it that way.
- **Recovery** (v0.7, [`recovery.md`](docs/research/recovery.md)): a refused turn is never retried; a rewind never rolls baton's record back; a crashed lead comes back (`internal/cli/recover.go`); `state.HereGate` holds edits and landings while a `verify --here` gate runs. Since v0.8.4 the host never gives up on a crash loop: past `state.MaxRecoveries` in `state.RecoveryWindow` it tries again after `Timing.RecoverAfter` (5 minutes), then every `RecoverEvery` (15). An API error a fresh context avoids (`state.StopError.Afresh`: prompt too long, a request too large, a broken tool history) starts the lead (`loop/afresh.go`) or a phase agent (`Coordinator.erred`) afresh from its brief, with the same backoff; refusals, logins, billing and an unknown model stay the human's.
- **Stuck edges** (v0.8.4): a verify job whose log has not grown and whose process tree used no CPU for `Timing.HungAfter` (20 minutes) is stopped as unverified (`loop/jobs.go` `hung`, `procs.TreeUsage`; never on log silence alone, so a platform that can't read CPU never stops one). A landing held by the lead's overlapping uncommitted files mails the lead to commit them by path after `Timing.LandNudge` (10 minutes); one held by a checkout off the run's branch is pushed once. A phase agent the human stopped (`loop/stopped.go`, `state.Worker.Stops`) is asked about on the lead's screen; at `escalation_timeout` baton decides from the record (`state.Satisfied`): work done lets the agent go and lands it, otherwise a first stop restarts it and tells the human, and a second takes it down and asks with no deadline (the question steps aside after `escalation_timeout`, and comes back when the human writes). Where the mod runs, a phase agent's permission prompt holds only that agent (`Loop.dialogHolds`, `state.Dialog.Phase`; spike 36), while serial mode holds on every dialog, since a typed key would answer the agent's prompt.
- **The mod** (`plugin/hooks/baton.js`) is a thin executor: it spawns and messages phase agents, asks the human, compacts the lead and submits baton's lines to it, drops agents' reports before the lead's model sees them, draws the band, and reports what it sees; it decides and words nothing. It asks from its band's render hook, never its timer, and its `tool.call` hook settles baton's questions, and the lead model's own (`hooks.Bound`: its Recommended option, else its first), at their deadline ([spike 34](spikes/34-ask-deadline/)); serial mode leaves the model's own questions to the human. The host asks for the lead's compaction once its Stop hook has run, a moment before Claude Code counts the turn over, so the mod holds a compaction Claude Code declines while the lead's turn runs (by the mod's own `turn.start` and `turn.complete`) and calls it from that turn's `turn.complete`, once ([spike 37](spikes/37-compact-at-turn-end/)); past `HOLD_MS` (30 seconds, within the host's `modAckWait`) it acks the refusal, and the host asks again after the turn (`loop.redo`). Run `make mod-test` and `claude plugin validate plugin` before committing a change to it, and never edit it while a session that loaded it runs.
- **The bridge** (`internal/bridge`): numbered command files under `.baton/runs/<run>/mod/`, each for one host instance, and reports through `baton mod report`, each recorded once. No hello from the mod, or one in another `bridge.Protocol`, means a serial run (`loop/mod.go`); after a restart of a run whose mod said hello, the host waits up to `Timing.ModHello` for the new claude's mod before it gives the session anything. When the host drives another run (a carried run, `Loop.drive`), it issues `bridge.Moved` in the old run's bridge; the mod says hello on the new one and starts its command count afresh, since the count is per run.
- `plugin/` is the Claude Code plugin: the skill, the launchers, the Stop hook that finishes `/baton start`, and the mod. `SKILL.md` is a stub that loads `internal/skill/skill.md` from the binary, so edit that, and never put `$ARGUMENTS` in the stub's inline command ([spike 18](spikes/18-skill-inject/)). `.claude-plugin/marketplace.json` makes this repo its own marketplace.
- `spikes/` holds archived experiments. Don't import from them.

## Commands

```sh
make build      # ./dist/baton for this machine
make test       # unit tests
make mod-test   # baton's mod under Claude Code's test kit (needs claude; calls no model)
make cross      # all release targets into ./dist
make e2e        # real-claude scenarios (needs BATON_E2E=1, costs a few cents)
make release-prep VERSION=v0.1.0   # pin checksums + plugin version, then commit and tag
```

End-to-end tests run real `claude --model haiku` and assert on `events.jsonl` and hook logs, never the screen. Each session has its own `BATON_HOME` and `GNUPGHOME` and loads this repository's plugin with `--plugin-dir` (`noModPlugin` for serial mode). The harness sets `BATON_WORKERS=0` unless a scenario calls `StartAgents`, `BATON_TEST_LOAD=0`, and `BATON_AGENT_RAMP=5s` (phase agents start 2 minutes apart otherwise); `BATON_ABANDON_AFTER` shortens the wait before a run counts as abandoned, and `BATON_HOLD_LAPSE`, `BATON_BLOCK_LOOK`, `BATON_RECOVER_AFTER`, `BATON_RECOVER_EVERY` and `BATON_REPLAN_MAX` the holds, blocks, crash backoff and replans. `BATON_AUTO_REPLAN=0` keeps baton's own replans out of a scenario that would cue one. `Session.ApprovePermissions` stands in for the human on the model's own permission prompts only, leaving every question of baton's to its deadline. Allow rules name the exact command, since auto mode drops a broad one like `Bash(sh:*)`. `BATON_E2E_SONNET=1` adds the Sonnet scenarios. Run one `go test` process at a time: the mod's store file in `~/.claude` is shared. The sessions take the permission mode from your own Claude Code settings, so in auto mode agents' ends come back as hand-backs the mod drops (`mod_dropped`). Claude Code's Bash tool ends a foreground command after 2 minutes unless the model sets a timeout, so a scenario's plan that waits longer asks for one (`BATON_FOREGROUND_MAX` takes at most 10m).

## Conventions

- Go: standard library first; a new dependency needs a reason (current: `creack/pty`, `golang.org/x/term`, `golang.org/x/sys`, `gofrs/flock`).
- Commits: [Conventional Commits](https://www.conventionalcommits.org/), one coherent unit per commit, so `git log` reads as the story of the project.
- Tests: table-driven, next to the code; time-dependent logic takes an injected clock; no test provokes a refusal.
- Every user-visible action baton takes is announced in the session (`systemMessage` or the band) and logged to `events.jsonl`.
