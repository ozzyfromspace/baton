# 32 — what baton's bridge and phase agents still need to know (Claude Code 2.1.296, haiku, macOS arm64, 2026-10-12)

Question: spike 31 showed that a mod can start and steer phase agents. The design for v0.8 (phases as subagents of
the lead, [`docs/research/visible-workers.md`](../../docs/research/visible-workers.md)) assumes more: how a
message reaches an agent that is busy or compacting, what the human's `/compact`, `/clear`, Esc, Ctrl-C and rewind do
to agents, what a mod reload keeps, whether the mod can tell the settings hooks whose compaction it is, when the
lead's compaction boundary is written and when a rewake's brief arrives, how big an agent's context is, how baton's
question behaves beside other dialogs, what the human typing to an agent looks like, API errors and usage limits in
an agent, ending one, and many of them for a long time.

Harness: `run.py <scenario> <workroot>`, spike 31's, with these changes. Each session loads its own copy of the
mod (`<work>/mod`), since a mod reloads when its file is saved. The PTY's raw bytes are kept (`screen.raw`), so a
step's screen renders as drawn (`screen-<label>.txt`, through `pyte`). `hook.py` also records, at `PreCompact`,
`SessionStart(compact)` and `PostCompact`, how many entries the lead's transcript has and where its
`compact_boundary` entries are; a detached watcher logs when a new one appears (`BOUNDARY`). An asyncRewake
`PostCompact` hook for every trigger (`hook.py rewake`) waits up to 20 s for that boundary, the proof the compaction
was the lead's, then wakes the model with a 5,935-character brief (`SPK_REWAKE=1`). `proxy.py` passes the API
through, and fails the requests of one agent on demand (its prompt carries a marker). The mod (`mod/hooks/register.js`)
logs every event and call to `mod.jsonl.<instance>.<part>`, and has a `.catch` on its hooks. `timeline.py <work>`
merges both logs. Agents run `sh long.sh` (60 s) or `sh slow.sh` (25 s). Where a row says "from a timer", the mod
spawned the agent from a `$.clock.after` callback, as a command poll would.

| scenario | what | result |
|---|---|---|
| S0 | where the mod spawns from: a timer, inside a `command.run` hook, inside the band's `ui.render` hook; and (S0-try1) a timer that runs the spawning command through `$.command.run` | **This decides what the mod sees of the agent.** From a timer: only its `turn.complete`. Its tool calls, its settings events (`classic.*`) and its `session.compact` skip the whole module, and the mod's own `agent.spawn` hook does not run. From inside either hook: everything, including `session.compact` with the agent's `agentId` and its token counts. The cause is Claude Code's re-entry skip: a module never sees events that come from inside its own calls. From a hook only that hook is skipped; from a timer, which runs outside any event, the whole module is. The `.catch` handlers are not asked about these skips. Through `$.command.run` from a timer, the mod's own `command.run` hook is skipped: "no command.run hook answered it", and nothing spawns. A message sent from a timer to an agent spawned in a hook leaves it visible. One sent from a hook to an agent spawned from a timer leaves it blind. |
| S0b | a timer queues the spawn and calls `$.ui.invalidate`, and the render hook spawns: with nothing open, with the mod's question open, with `/tasks` open | It works, and the mod sees the agent fully. The render came 1.9 s after the invalidate. **The band is not drawn while a dialog or `/tasks` is open**, so the spawn waited until the question was answered (15 s) or `/tasks` closed (15 s). |
| S1 | messages to a running agent (`$.session.send`, and the SendMessage tool through `$.tool.call`), to an idle one, and to one the mod stopped with `TaskStop` | **A message to a running agent is queued to its next tool round:** `{"isDelivered":true}`, or "Message queued for delivery to … at its next tool round". Both arrived (`session.receive`, origin `coordinator`, plugin `spk`) when its 60 s command ended, and it did them before its own task. Nothing was lost or interrupted. To an idle agent either one resumes it ("Resuming agent …"; `SubagentStart` again). `$.session.send` is the SendMessage tool too: the lead's `PreToolUse` and `PostToolUse` fire for `SendMessage`, with a `toolu_plugin_…` id. `TaskStop` from the mod ends a running agent: "Successfully stopped task", `turn.complete` `reason: aborted`, and the agent leaves the list. **A later message resumes it.** Each resumed run reported to the lead as a `task-notification`, which the mod dropped. Claude Code's own forks of a running agent (about every 30 s, likely its progress summary) fire hooks with an `agent_id` of their own, an empty `agent_type` and the agent's worktree as `cwd`. One fired a `PreToolUse` for the agent's command with no `PostToolUse` after it. |
| S2 | an agent spawned in a hook compacts by itself (small window): the mod's `classic.*` hooks stamp `spk_loop` on the compaction events; a message sent at its `session.compact`; then the lead's `/compact` | The mod's `session.compact` (with `agentId`) runs before `PreCompact` and resolves after `PostCompact`, so it brackets the settings hooks. **The stamp reaches the settings hooks** (`spk_loop` in their input, the agent's id, or `main` for the lead's). But the mod's `classic.PreCompact` has an `agent_id` key with no value, so the mod can name the loop only from its own bookkeeping (which `session.compact` is open), which two loops compacting at once would confuse. The agent's compaction hooks share its `SubagentStart`'s `prompt_id`. **A message sent during the agent's compaction** came back `isDelivered` and arrived at its first tool round after it. The lead's transcript got no new boundary in 30 s, so the rewake found no proof and did not wake the lead. The lead's own `/compact`: boundary 164 ms after `PostCompact`, the rewake's proof at 160 ms, the brief answered (OSPREY). |
| S3 | a typed `/compact` in the lead while two phase agents run | It compacts at once; both agents go on, nothing lost. The boundary is written **175 ms after `PostCompact`** (the transcript had 43 entries at the hook and the boundary is entry 44). The rewake's proof came at 182 ms; its brief reached the idle lead as a prompt whose `origin.kind` is `task-notification`, as an agent's report is, and was followed. The lead's `Stop` lists both agents in `background_tasks` with `"agent_type": "spk:phase"`, status `running`. |
| S4 | the lead compacts by itself mid-turn (small window); the rewake registered for every trigger | The mod's `session.compact` (`trigger: auto`, no `agentId`) brackets the hooks; boundary 174 ms after `PostCompact`; the rewake's proof at 215 ms. **The brief arrived within the running turn, at its next tool round** (`UserPromptSubmit` mid-turn), and the model followed it (OSPREY, not the task's FINISHED). |
| S5 | Esc and Ctrl-C during a lead turn, a rewind, and `/clear`, while a phase agent runs | Esc and Ctrl-C abort the lead's turn alone (`turn.complete` `aborted`); the agent runs on. The rewind keys of v0.7's e2e (Esc Esc, Up, Enter, 2) picked **"Summarize from here"**: with no code changes the options are Restore conversation, Summarize from here, Summarize up to here, Never mind, so a rewind there compacted the lead (`PreCompact manual`, a boundary). **`/clear` ended the idle agent:** `SessionEnd clear` and `SessionStart clear`, the agent went from `idle` to `completed` and left the list, and a message to it after was refused: "could not be resumed: No transcript found for agent ID". |
| S5b | a rewind that restores the conversation (option 1), then `/clear`, each while agents run | The rewind fires no hook, and the agent runs on. **`/clear` killed both running agents' commands** (`PostToolUseFailure`, exit code 137), not the agents: they ran the command again and finished, their hooks now with the new session's id. A message after was refused: "is stopped (completed) and could not be resumed: … its worktree is not recorded for this isolated agent". |
| S6 | the mod's file saved mid-run, then `/reload-plugins`; hooks that throw (a tool call, a prompt, a compaction), their `.catch` rethrowing | The save reloads the module: a new instance, `session.start` again, timers restarted (the old instance's stopped), `$.store` kept (a counter and the agents' ids), the commands and the agent type registered again. The running agent went on, and its `turn.complete` reached the new instance. `/reload-plugins` with nothing changed reloads nothing. A hook that throws lets the event through: the command ran, the prompt reached the model ("through"), the compaction ran. |
| S7 | `$.ui.ask` during a lead turn, while a permission prompt is open in the lead, and alone; each answered by typing 3, as baton's host does at a deadline | During a turn the dialog opens at once, and the lead's command runs on beneath it. With a permission prompt open, the ask's `PreToolUse` and `PermissionRequest` (no `agent_id`, a `toolu_plugin_…` id) fire at once, but the permission prompt stays in front. **The 3 went to it, and in 2.1.296 a permission prompt's third option is "Yes, and switch to auto mode"** (1 Yes, 2 Yes and don't ask again for `python3 *`, 3 Yes and switch to auto mode, 4 No). The command ran and the session stayed in auto mode; then the question showed, and a second 3 answered it ("Let baton decide"). Alone, 3 answers it. |
| S8 | the human in the agent panel: opening a running agent's transcript and typing to it, then leaving with Esc | The panel under the prompt has a row per agent (`◯ T1  T1 — spike phase  6s · ↓ 29.6k tokens`) below `main`; ↓ selects, Enter opens the agent's transcript with a `Message @T1…` box. **A typed message raises no hook** (no `prompt.submit`, no `UserPromptSubmit`): the row shows "1 queued". **Esc in that view interrupted the agent:** `turn.complete` `aborted`, status `killed`, no `SubagentStop`. Its queued message waited. The driver's next keys went to the agent's box, still open, and when sent they resumed it. The resumed agent took the interruption for a rejection: "I haven't run anything since your rejection, and I won't re-run `sh long.sh`". |
| S8b | x on a running agent's row, with focus in the panel | ↓ selects the row ("Enter to view · x to stop · ctrl+x ctrl+k to stop all agents"). **x stops the agent:** `turn.complete` `aborted` at once, status `killed`, no `SubagentStop`. The row stays ("x to clear"). **Every message after is refused** by both routes: "was stopped by the user and was not resumed. Treat its work as cancelled; only start a new agent for it if the user explicitly asks." So an agent stopped by x and one interrupted by Esc in its view (S8) look alike until a message is sent: the first is refused, and the second resumes. |
| S9 | API errors in an agent through `proxy.py`: a 400 once, 529 three times, a 429 with the subscription's rate-limit headers (`anthropic-ratelimit-unified-status: rejected`) | Claude Code retried the 400 and the 529s, and the agent's turn ended normally. **The 429 ended the agent's turn at once:** `turn.complete` `reason: error` (123 ms), `StopFailure` with the agent's `agent_id` and `error: rate_limit`, status `failed`. A message once the limit was lifted resumed it, and it finished. |
| S10 | four agents for 20 minutes, each sent its next round by the mod when it ends a turn | Stable. 156 agent turns (38 to 39 each), all ending `answer`; 151 messages, all delivered; 152 reports to the lead, all dropped before its model, which had no turn but its first. claude's resident memory stayed between 286 and 445 MB, sampled every 30 s, with no growth (286 MB at the end). |

Also measured:

- **An agent's context.** The last assistant entry of its transcript (`subagents/agent-<id>.jsonl`) gives the context
  the agent has (`input_tokens + cache_read_input_tokens + cache_creation_input_tokens`): 249,071 before it compacted,
  against the boundary's `preTokens` of 255,712, which adds the last tool result. Under the same override the lead
  compacted at 250,847: an agent compacts where the lead does. Its `agent-<id>.meta.json` names its type, worktree,
  name and the spawning `toolUseId`; `SubagentStop` gives its transcript as `agent_transcript_path`.
- **`$.store` is one file per plugin** (`~/.claude/plugins/store/spk_inline-<hash>.json` for a `--plugin-dir` plugin),
  shared by every session that loads it: all of this spike's sessions wrote to the same one (the mod kept its keys
  apart by scenario). The spike's file was removed afterwards.
- **The validator** (`claude plugin validate`) checks a mod statically: `$.env.get` takes a literal name; `$` is
  passed only to functions declared at the top of the file; a `.catch` handler is a function literal or the name of
  one.
