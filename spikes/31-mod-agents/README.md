# 31 — phase agents a mod starts and steers (Claude Code 2.1.296, haiku, macOS arm64, 2026-10-12)

Question: v0.5–v0.7 run each worker as a hidden `claude` in a pseudo-terminal of baton's own. baton can steer them
exactly, but the human can't see them: how many run, on what, whether anything runs at all. Could a phase run as a
**subagent of the lead session** instead (shown by Claude Code in its own agent panel, `/tasks` and `/workflows`),
with baton still in control, deterministically, with no model judgment?

Harness: `run.py <scenario> <workroot>` runs `claude --model haiku --permission-mode acceptEdits --plugin-dir mod
--settings <hooks>` in a PTY (`../common/scenario.py`) in a fresh git repo, under a venv with `pyte` for screen
dumps. `mod/` is a plugin whose hooks module (`mod/hooks/register.js`) is a **mod**: JavaScript Claude Code runs in
its own process, with an API to spawn agents, message them, compact, submit prompts and draw. It logs every event
it sees and every call it makes to `mod.jsonl`, and adds `/spk-*` commands the driver types to trigger each step.
`hook.py` is a settings hook on every event, logged to `hooks.jsonl`: it gives each subagent a codeword at
`SubagentStart`, blocks each subagent's first stop with one more instruction (`SPK_BLOCK_STOP=1`), approves a
`Workflow` call (`SPK_ALLOW_WORKFLOW=1`), and makes the worktree at `WorktreeCreate` the way baton does (outside
the checkout, on a branch of its own). A mod's file reloads when saved, so it must not be edited while a scenario
runs (scenario A's later steps were lost that way).

| scenario | what | result |
|---|---|---|
| A | `$.agent.spawn({prompt, name, description, cwd})` for P1 and P2 | Both start at once as **background** `general-purpose` agents on the session's model, named, with `spawnedBy: spk`. `$.agent.list()` gives each one's status (`running`, `idle`, `waiting` for its own background Bash, `completed`). Every tool call reaches the mod's `tool.call` with the agent's id, and every settings hook fires inside them with `agent_id` and `agent_type`. `SubagentStart`'s `additionalContext` reached the agent (it named the codeword), and a `SubagentStop` block ran it on with the reason as its next instruction. **`cwd` was ignored**: `pwd` was the checkout, and the files landed there. `$.session.compact()` from a `command.run` hook is refused ("call it from a later event"). Claude Code's own guard refused `sleep 25 && echo slept` ("To wait for a condition, use Monitor…"), so later scenarios sleep in `slow.sh`. |
| A2 | the Agent tool from the mod: `$.tool.call({tool: 'Agent', isolation: 'worktree', …})` | Refused: "runs the Agent tool: that is $.agent.spawn (host check)". `$.session.compact()` from a `$.clock.after` timer compacts the lead (the summary comes back). |
| A3 | `$.agent.register({name: 'phase', isolation: 'worktree', prompt, description})`, then `$.agent.spawn({subagentType: 'spk:phase', …})` | **Works.** `WorktreeCreate` fires once per agent with `name: agent-<agentId>`, and the agent works in the path the hook returned: `bwt-agent-<id>` on `baton/spk/agent-<id>`, outside the checkout. Its `SubagentStart`, tool hooks and `SubagentStop` carry that `cwd`. Compacting the lead (from a timer) while both agents ran left them running. A message to an idle agent (`$.session.send({to: {agentId}, text})`) resumed it with its context (SubagentStart again) and it did the new task in its worktree. That resumed run's report reached the **lead's model** as a `<task-notification>` prompt, and the lead acted on it (it tried to read the worktree's file and sat on the permission prompt). `$.prompt.submit` from `command.run` is refused like the compaction. An agent leaves `$.agent.list()` about 100 s after it goes idle. `SubagentStop` also fires for Claude Code's own internal agents (the compaction summary and others), with an empty `agent_type`. |
| B | P3 runs `date`; then resumed by a message; then `$.prompt.submit` from a timer | `date` needed no permission, so the permission prompt is still to see. The resumed run's report arrived at the mod's `prompt.submit` with `origin.kind: task-notification`, and **`{drop}` kept it from the lead's model** (no `UserPromptSubmit` for it). `$.prompt.submit` from a timer started a lead turn, `origin: {kind: plugin, name: spk}`. The human's own prompts arrive with `origin.kind: composer`. The agent panel row reads `◯ P3  P3 — spike phase  0s`. |
| C | `kill -9` of claude while P2 runs `slow.sh`; `claude --resume <session>`; `$.session.send` to P2's old id | After the resume `$.agent.list()` is empty, but the message **was delivered and resumed P2** with its conversation, in its worktree: it ran the interrupted `slow.sh` again, wrote `p2.txt`, then did the new task. Its report went to the lead (the new mod didn't know its id, so didn't drop it). |
| W1 | a saved workflow (`.claude/workflows/spk-plan.js`: P1 and P2 at once, P3 after P1, P4 in a worktree) started by the mod: `$.tool.call({tool: 'Workflow', name})` | Refused: "runs the Workflow tool, whose agents run outside the at-once bound on spawns: $.agent.spawn is the door (host check)". |
| W2 | the same workflow started by typing `/spk-plan` | The typed command is a prompt (`UserPromptSubmit /spk-plan`), and the **lead's model** then calls `Workflow` (a `PreToolUse` hook approved it). It ran as planned: P1 and P2 at once, P3 after P1, P4 in a worktree made by the `WorktreeCreate` hook (`name: wf_<run>-3`, a run's name, not a phase's). Workflow agents are `workflow-subagent`s, spawned through `agent.spawn` (origin `engine`): their settings hooks fire with `agent_id`, `SubagentStart` context reached them, and the mod saw each one's `turn.complete`. **A workflow agent's turn is its whole life**: P2, whose `slow.sh` went to the background, ended its turn "Waiting for the background sleep to finish before I reply DONE", and that was its result. The finished workflow reached the lead's model as a `task-notification`. The rendered `/workflows` screens were too garbled to read. |
| D1 | P4 runs `python3 -c …`, which needs permission; then `$.ui.ask` from a timer | The `PermissionRequest` hook fired **with the phase agent's `agent_id` and `agent_type`**, Claude Code's `permission_prompt` notification fired, and the prompt was in the main session; Enter approved it and the agent went on. `$.agent.list()` kept saying `running` meanwhile, so the hook is how baton knows a phase waits on the human. `$.ui.ask` opened Claude Code's own question dialog in the main session (a `PreToolUse`/`PermissionRequest` for `AskUserQuestion` with no `agent_id`), and Enter's answer, `Go ahead`, came back to the mod, not to a model. |
| D2 | P5 reads four ~25k-token files under `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE=25` | The agent **compacted by itself** (`compact_boundary` in its transcript; the mod's `session.compact` with its `agentId`) and still knew the codeword from `SubagentStart` (the summary kept it; `SubagentStart` did not fire again). **The settings hooks for it look like the lead's compaction**: `PreCompact(auto)`, `SessionStart(compact)` and `PostCompact` came with no `agent_id`, the lead's `cwd` and the lead's transcript; only `prompt_id`, the agent's, differs. |

Not seen here: what the agent panel, `/tasks` and `/workflows` look like to a person (the PTY's screens did not render
cleanly), typing into a phase agent's transcript, a usage limit in a background agent, and phases that run for hours.
